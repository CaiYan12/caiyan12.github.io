# SPEC：将 AI日报迁为独立项目并保留原访问入口

日期：2026-10-28。

状态：规格及测试边界已确认，已发布为 [CaiYan12/ai-news #1](https://github.com/CaiYan12/ai-news/issues/1)，标签为 `ready-for-agent`。公开仓库和本地工程约定已建立；尚未拆票或实施应用迁移。

> 归档注记（2026-10-29）：本文为 2026-10-28 计划期记录，状态行保留当时原文（「尚未拆票」写在拆票之前）。实施结果：七张实施票中，`CaiYan12/ai-news` #2–#7 承载 T1–T5 与 T7，主站 #109 承载 T6（跨仓单列，不重复计入 ai-news 票数），七个 Issue 均已关闭；父规格 `CaiYan12/ai-news` #1 仍为 OPEN，未关闭、未改写。

## Problem Statement

站长希望长期经营 AI日报这一独立阅读产品。它目前作为主站内的独立 React 页面存在，仍依附于主站的工程配置、构建、测试和部署；日报的小改动需要随博客一起发布，后续维护也容易混用两个项目的上下文。

拆出独立项目时，读者仍应通过原来的入口和详情链接继续阅读，原有阅读记录、收藏、稍后阅读和设置不能因迁移被重置。站长需要获得可以独立维护和发布的项目，同时有明确的上线验收、失败恢复和后续会话交接。

本需求解决项目归属及构建发布耦合，不把搬迁本身视为客户端资源瘦身或性能提升的证据。

## Solution

建立公开的 `CaiYan12/ai-news` 仓库，以 Vite + React + TypeScript 承载现有 AI日报应用，通过 GitHub Pages 继续提供 `https://caiyan12.github.io/ai-news/`。

首次独立发布保持现有单源阅读产品的功能与视觉，仅调整独立运行、测试、工程配置和部署所必需的部分。应用保留五套模板、亮暗模式、通用阅读路径、用户数据和现有过渡行为。主站保留入口与完整文档导航，新项目保留返回主站入口。

新项目建立时执行 `/setup-matt-pocock-skills`，建立自己的工程约定、GitHub Issues 入口、默认分流词表和单上下文领域文档规则。以当前稳定代码建立新的初始提交，并通过迁移说明追溯原主站代码与历史。

先验证本地新旧行为和生产构建产物，再执行有恢复方案的发布切换。线上验收与主站清理完成后，由站长在 Codex 建立新的 `ai-news` 项目，接手日常更新。

## User Stories

1. 作为日报读者，我希望继续使用原来的 `/ai-news/` 地址，以便已有书签和分享链接仍然可用。
2. 作为日报读者，我希望从主站桌面和移动导航进入日报，以便入口位置与使用方式保持一致。
3. 作为日报读者，我希望从日报顶栏和页脚返回主站，以便继续访问博客内容。
4. 作为日报读者，我希望已有单期详情链接可以直接打开和刷新，以便分享的内容仍可定位。
5. 作为日报读者，我希望浏览器前进、后退及页面内返回保持现有语义，以便不会迷失阅读位置。
6. 作为日报读者，我希望继续浏览相同的期号列表、标题、时间、摘要和来源，以便迁移不改变内容理解方式。
7. 作为日报读者，我希望继续搜索和按分类筛选，以便找到需要的内容。
8. 作为日报读者，我希望继续按全部、未读、收藏和稍后阅读筛选，以便管理自己的阅读进度。
9. 作为日报读者，我希望各筛选维度的数量和全部标为已读功能保持原有含义，以便不会因迁移误判阅读状态。
10. 作为日报读者，我希望进入详情和切换已读状态时保留原有操作方式，以便沿用已有习惯。
11. 作为老读者，我希望迁移后已有已读、收藏和稍后阅读记录仍然匹配原期号，以便不用重新整理。
12. 作为老读者，我希望迁移后原有主题、布局、模板和缩放设置继续生效，以便不用重新设置。
13. 作为老读者，我希望后续读取和写入仍使用兼容的数据格式，以便发布失败恢复旧版本时不会再丢失状态。
14. 作为日报读者，我希望收藏与稍后阅读仍可独立切换，以便两种用途互不覆盖。
15. 作为日报读者，我希望继续使用跟随系统、固定亮色和固定暗色模式，以便适应不同阅读环境。
16. 作为日报读者，我希望亮色和暗色各自记住主题与定制风格，以便切换外观后保留偏好。
17. 作为日报读者，我希望五套橘鸦模板的列表和详情保持原有视觉，以便独立发布不变成页面改版。
18. 作为日报读者，我希望关闭定制风格或结构化解析不适用时继续使用通用阅读路径，以便内容仍可阅读。
19. 作为日报读者，我希望保留紧凑列表、卡片网格、杂志风及其现有列数和显示字段设置，以便沿用自己的布局。
20. 作为日报读者，我希望内容缩放仍只作用于列表或正文，以便顶栏和阅读工具条维持可用尺寸。
21. 作为日报读者，我希望正常切页、快速连续导航和减少动态效果偏好得到现有处理，以便迁移不引入闪屏、卡住或未处理异常。
22. 作为日报读者，我希望原文和正文外链继续按既有方式打开，以便阅读页面不会意外丢失。
23. 作为日报读者，我希望仍能手动刷新并使用已有定时刷新设置，以便获取更新。
24. 作为日报读者，我希望实时订阅源失败时仍尝试内置快照并明确说明当前来源，以便不会把旧快照误认为实时内容。
25. 作为日报读者，我希望已有缓存可以继续按原策略显示，以便迁移不主动制造空白首屏。
26. 作为日报读者，我希望获取内容失败时保留既有提示，以便知道当前发生了什么。
27. 作为日报读者，我希望历史保留天数和手动清除数据仍遵循原有设置与确认流程，以便迁移不擅自清除记录。
28. 作为禁用 JavaScript 的访客，我希望页面保留既有说明，以便理解日报需要 JavaScript，不会面对无法解释的空白页。
29. 作为窄屏读者，我希望筛选、设置和阅读工具仍然可用，以便手机尺寸下可以完成基本阅读。
30. 作为读者，我希望外部内容的现有 HTML 消毒与安全外链边界被保留，以便迁移不削弱已有保护。
31. 作为站长，我希望新项目可以独立安装、检查、构建和发布，以便日报更新不再依附主站流水线。
32. 作为站长，我希望新项目有明确的工程约定和需求入口，以便后续会话能按一致流程维护。
33. 作为站长，我希望新项目记录来源仓库、基准提交和历史链接，以便新初始提交仍可追溯已有开发过程。
34. 作为站长，我希望项目说明区分应用代码、订阅内容和第三方资产，以便公开发布时准确表述来源与许可。
35. 作为站长，我希望旧数据或关键行为验证失败时停止切换，以便不把迁移问题交给读者承担。
36. 作为站长，我希望发布失败时有可执行的恢复步骤，以便尽快恢复原入口服务。
37. 作为主站维护者，我希望移除经核实不再需要的旧应用和依赖，同时保留入口检查，以便主站职责清晰且不留下死链接。
38. 作为后续维护者，我希望获得独立项目的位置、部署状态、验收证据与遗留事项，以便在新的 Codex 项目中接手更新。
39. 作为站长，我希望拆仓成果与性能优化成果分别记录，以便不会把组织调整误报为资源体积或加载速度改善。

## Implementation Decisions

### 已确认的架构与产品边界

1. 新项目采用 Vite + React + TypeScript，保持纯静态部署和现有浏览器端阅读方式，不引入应用服务器、SSR、账户系统或新的存储服务。
2. 首次发布保留现有 React、React DOM、Zustand、Lucide 与 DOMPurify 的应用行为及版本起点。新增构建工具的版本、引擎兼容性与锁文件应在实施前核实并记录，不顺带升级无关依赖。
3. 应用独立承担入口文档、元数据、样式构建、主题、模板、状态、订阅源和发布。不得以引用主站本地源码或旧构建资源的方式维持表面独立。
4. 新浏览器标题为“AI 日报”；保留现有界面、图标和返回主站入口。新项目独立配置标题和描述，不再通过主站站点配置取值。
5. 五套定制风格全部保留；亮暗各自的选择、通用阅读路径、布局和交互保持既有语义。拆仓不裁剪模板、不增加产品功能，也不借机重构状态管理。

### 地址、数据与运行时契约

6. 公开地址继续为 `https://caiyan12.github.io/ai-news/`，沿用首页 hash 和以 `#/issue/` 加转义 GUID 构成的详情链接，不迁移为新的路径路由。
7. 新项目资源使用 `/ai-news/` 公共基路径，独立提供所需 JS、CSS、图标和内置快照；不依赖主站旧的 Astro 哈希资源。动态拼接的快照地址不得重复包含项目路径。
8. 快照的最终公开地址继续为 `/ai-news/snapshot/juya.xml`，订阅源身份保持 `juya-daily`，实时订阅地址保持 `https://daily.juya.uk/rss.xml`。
9. 保持存储键 `ai-daily:v1`、实际持久化版本字段 `version` 的值 1，以及 GUID 对应关系。迁移不新增清空、重置、改键或不兼容写入，也不改变已有历史保留策略。
10. 将用户主动保存的已读、收藏、稍后阅读和设置，与可重新获取的文章缓存分别验证。既有保留天数和用户主动确认的数据清除仍遵循旧语义，不承诺超出原策略的永久保存。
11. 保留实时读取、缓存显示、订阅源失败后的内置快照尝试及现有来源提示。首版不增加快照定时更新服务、代理、Service Worker 或完整离线应用承诺。
12. 保留现有内容消毒和外链行为，不以迁移为由移除 DOMPurify 或放宽已存在的内容边界。
13. 列表与详情的 View Transitions 行为及不支持该能力、减少动态效果时的现有路径均需保留。新启动入口不得因挂载方式变化产生重复监听、定时任务或重复导航。
14. 样式配置只提取日报实际需要的映射与处理链。改变工具类扫描范围后，必须用相同数据核对新旧渲染，不能以源码相似或 CSS 文件名相似代替视觉证据。

### 工程归属与发布

15. 目标仓库为公开的 `CaiYan12/ai-news`。使用新的初始提交，保留原主站仓库、基准提交和相关历史链接作为来源记录；不直接搬入混有主站改动的完整提交。
16. 新项目建立时执行已确认的工程技能初始化，建立独立的需求入口、默认五个分流标签、工程约定和单上下文文档规则；不能把主站已有配置或本规格草案视为新项目已初始化。
17. 新项目的规格和实施任务进入其 GitHub Issues，通过 gh CLI 操作；跨仓操作必须显式指定仓库。主站变更保留清楚的归属及互链，不能把日报规格误发到主站代替约定的入口。
18. 应用代码按已确认的 MIT 方向发布；订阅内容和第三方资产保留各自来源及声明。具体来源和许可归属属于公开发布前的事实核查，不以目录关系或新初始提交推断原创与授权。
19. 新项目有独立的检查、构建和 Pages 发布流程；不复制主站的 Giscus、文章、项目目录、贡献日历或其他定时取数任务。
20. 主站保留桌面和移动日报入口与完整文档跳转。新项目验收后再清理旧实现和已核实不再需要的依赖；依赖清理必须区分客户端运行时、类型与 OG 构建用途。
21. 新旧站点同一路径的发布关系、缓存影响和切换顺序必须实际验证。接受受控切换窗口，不提前承诺零中断；切换前应保存可恢复的旧产物、对应提交和恢复步骤。
22. 兼容性验证失败时不正式切换；线上发现关键功能或数据问题时恢复服务并明确记录未通过项，不能靠删除判据完成验收。
23. 当前会话在后续获得相应授权后负责迁移至上线验收与结案。站长随后自行创建新的 Codex 项目，承接日常更新；不由本会话代建 Codex 项目或向其他会话派发工作。

## Testing Decisions

### 主测试边界：浏览器中的完整使用流程

主要沿用已有日报 Playwright 烟测的最高层边界：让真实浏览器载入生产构建，通过实际入口、控件、URL 和可见内容验证读者行为。应用内部组件拆分、函数调用次数或框架专有 DOM 不是通过标准。

原有主站与日报混合烟测拆分为应用自身行为及主站入口集成职责，不能简单删掉旧检查。原先依赖 `astro-island` 的判断改为内容接管与无 JS 说明的行为断言。

| 编号 | 浏览器旅程           | 通过标准                                                                                                                                 |
| ---- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| T1   | 独立入口与路由       | 原入口可载入新应用；标题为“AI 日报”；列表到详情、直接打开详情、刷新、返回、浏览器前进后退均符合既有语义；未知期号保留既有反馈            |
| T2   | 老用户状态继承与回写 | 同一 origin 顺序运行旧、新产物，读取旧版真实格式的测试数据；记录、设置和 GUID 对应关系不丢失，新应用操作可正确回写；恢复旧产物后仍可读取 |
| T3   | 原有阅读与设置       | 搜索、分类、阅读状态筛选、计数、批量已读、收藏、稍后阅读、布局、主题、缩放、刷新设置和主动清除确认保持原行为                             |
| T4   | 数据来源与内容回退   | 固定订阅数据保证可重复；精确制造实时源失败时加载内置快照并显示来源；结构化模板不适用时通用阅读可用，现有消毒边界保留                     |
| T5   | 视觉与切页           | 五套模板 × 亮暗 × 列表/详情的 20 种组合与旧产物对照；覆盖正常及快速连续导航、减少动态效果与不支持 View Transitions 的路径                |
| T6   | 主站与发布集成       | 主站桌面和移动入口真实可进入日报，顶栏及页脚真实可返回主站；公开入口和所需静态资源确为新项目发布产物；主站再次发布后入口仍然有效         |
| T7   | 无 JS 与异常观察     | 禁用 JS 时保留既有说明，启用后说明被应用内容替换；逐旅程收集页面异常与控制台错误，不能用主站 A-8 通过的结论代替日报自身检查              |

### 数据、视觉与异常的核对方法

- 旧状态继承测试使用隔离浏览器上下文和可追溯测试数据，不在站长常用浏览器中清空存储。相同 origin 必须包含相同协议、主机和端口；不能把两个不同端口的独立运行称为已验证数据继承。
- 用旧版格式与真实可用 GUID 构造已读、收藏、稍后阅读、非默认主题/布局/缩放，区分缓存存在与不存在的场景；测试时间与历史保留设置应避免把既有过期清理误判为迁移丢失。
- 视觉比较使用相同订阅数据、外观设置、字体环境和视口，区分明确批准的标题变化与页面漂移。默认覆盖 1280×900 桌面和 390×844 窄屏两组视口；两组均检查 20 种模板组合及可完成阅读的关键控件。
- 正常与快速导航使用状态、动画事件和实际渲染结果判断，不用固定等待时间代替过渡完成；不把最终截图正常等同于过程中没有闪屏。
- 已有实时 RSS 失败日志只能在预期的回退场景内结合实际快照结果解释；保留原始记录，不新增宽泛的第三方错误忽略列表。新出现的错误应追溯基线与迁移因果后处理，不顺带纳入无关修复。
- RSS 整站断网不等于快照可用：快照尝试依赖页面资源或已有缓存可访问。本规格不把“内置快照回退”写成首次访问完全离线也可用。

### 必要的辅助验证

1. 新项目在不读取主站源码目录的条件下安装、类型检查和生产构建，锁文件可复现，所有必需资源按公共基路径解析。
2. 优先通过浏览器流程覆盖持久化和地址解析；只有迁移适配需要独立覆盖时，才沿已有存储、hash、订阅解析等接口增加输入/输出测试，不为未改变的内部实现补镜像测试。
3. 主站清理后完成主站类型检查、构建及受影响入口验证，保留私有文章分类/标签路由检查既有的页面清单来源；不把删除日报实现扩大为 sitemap 全站策略改造。
4. 发布证据必须分别记录本地检查、远端 SHA、CI、Pages、实际浏览器行为及恢复结果。HTTP 200、资源体积数字或流水线绿色均不能单独证明迁移成功。
