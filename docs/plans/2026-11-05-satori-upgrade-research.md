# Satori 0.26.0 → 0.63.2 调研：隔离探针取证

> 本文只回答「能不能装、能不能渲染、差异是什么性质」，**不出 spec、不拆票、不改 `package.json`**。所有数字都出自 `output/satori-upgrade/probe/` 下可复跑的探针，主项目依赖与源码全程未动。

## 结论摘要

README TODO 要求先答三个问题，实测答案如下：

| 问题              | 结论               | 依据                                                                                                                                                           |
| ----------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 能否装上          | **能**             | `npm install` 12 秒、22 个包、无原生编译，`--ignore-scripts` 不影响                                                                                            |
| 能否渲染 33 张 OG | **能，33/33**      | 与线上同源的字体、同源模板、同尺寸 1200×630，全部出图                                                                                                          |
| 差异性质          | **三类，性质不同** | ① 盒模型与 flex 收缩语义变了 → 全部错版，两行改动可复原；② 文本度量漂移 ±0.9% → 16/33 张标题换行点改变；③ 空串子节点不再占 `gap` → 唯一无描述那篇整体下移 10px |

一句话：**这不是「改个版本号就能上」的升级**。默认写法下 33 张全部渲染成功，但**每一张都错版**——根容器从 1200×630 变成 1320×750，底部「作者｜日期」整行掉出画布。两处一行改动能把几何完全复原，且这两处改动在 0.26.0 上是**逐字节无操作**，可以先落地再升版本。复原后仍有 16 张标题的换行点与旧版不同、1 张整体下移 10px，这部分属于产品观感问题，需要站长裁定。

## 1. 探针怎么跑

```bash
cd output/satori-upgrade/probe
node render.mjs --satori <模块路径> --out <目录> [--fix-box-sizing] [--fix-flex] [--all-nodes] [--only <slug>]
node compare.mjs --a <目录> --b <目录> [--threshold 8] [--out <json>]
```

| 脚本               | 作用                                                        |
| ------------------ | ----------------------------------------------------------- |
| `render.mjs`       | 按真实模板渲染全部非草稿文章，落 SVG + PNG + 节点盒 + 耗时  |
| `compare.mjs`      | 两张 PNG 转 raw RGBA 逐像素比，出最大差 / 平均差 / 差异占比 |
| `box-model.mjs`    | 同一根容器四种写法在两个版本下的实际盒尺寸                  |
| `flex-shrink.mjs`  | 绿色竖条与标题的 flex 收缩分配                              |
| `text-metrics.mjs` | 同一串文本两个版本下的自然宽度                              |
| `clamp.mjs`        | 超长标题的三行截断与省略号                                  |
| `line-corr.mjs`    | 逐行墨迹横向分布相关性，用来判定「换行是否变了」            |
| `band-diff.mjs`    | 按标题区 / 描述区分开统计差异                               |
| `diff-image.mjs`   | 生成 ×8 放大的差异图，用来看差异形态                        |

字体在 `fonts/`（regular.ttf / bold.ttf，各约 10.5 MB），由站点同一个 CSS2 URL 抓取：不带 User-Agent 时 Google Fonts 返回 **TTF**（`format('truetype')`），与 0.26 时代一致，不是 WOFF2。

**模板来源**：`render.mjs` 里的模板逐行抄自 `src/pages/og/[...slug].png.ts:118-302`，只把字体改成读本地文件、头像用 sharp 预转 PNG。为验证抄得对不对，先用 0.26.0 复刻版对照**真实构建产物** `dist/og/`：

```
共同文件 33 / 最大单通道差 148 / 最大平均差 0.0239 / 差异像素合计 666 / 最大占比 0.028%
```

33 张、75.6 万个像素里只有 666 个超阈值，最大平均差 0.024——属字体文件版本漂移的亚像素级差异，**探针是忠实的**。

复刻时踩过一个坑，值得写下来：`postsSchema` 把 `description` / `excerpt` 都定义为 `.default("")`，所以无描述文章的 `description` 是**空串而不是 `undefined`**。空串作为 children 仍占一个 `gap` 间隔（高度 0，但间隔照算），去掉它会让内容整体偏移 10px。第一版探针用 `.filter(Boolean)` 把空串滤掉了，结果 `20260320000000` 这一张对不上（平均差 10.47），补回来才归零。

| ------------------------ | ----------- | ------------------------------------------------------------------------ |

### 2.2 依赖栈：比「opentype.js 换 harfbuzzjs」更彻底

README 只记了 `opentype.js → harfbuzzjs`，实际上**布局引擎也换了**：

| 项             | 0.26.0                               | 0.63.2                                             |
| -------------- | ------------------------------------ | -------------------------------------------------- |
| 直接依赖       | 11 个                                | 12 个                                              |
| 新增           | —                                    | `fflate@0.7.3`、`harfbuzzjs@0.10.0`                |
| 移除           | —                                    | **`yoga-layout@^3.2.1`**                           |
| 其余 10 个     | —                                    | 版本约束逐条相同，`:^` 都没动                      |
| 布局引擎       | `yoga-layout`（npm 包）+ `yoga.wasm` | 包内自带 `layout.wasm`（509 KB），不再依赖 yoga    |
| 导出子路径     | `./yoga.wasm`                        | `./layout.wasm`（**更名**），另加 `./experimental` |
| 包体（解压后） | 5.4 MB                               | **26 MB**                                          |
| `engines.node` | `>=16`                               | `>=16`（未变）                                     |

`@shuding/opentype.js` **仍在**依赖里（0.63.2 依旧列着 `1.4.0-beta.0`），HarfBuzz 是整形层新增，不是把 opentype 整个替掉。仓库里没有任何地方引用 `satori/yoga.wasm`、`satori/standalone`、`satori/jsx`（已 grep 确认），所以子路径更名对本仓库无影响。

### 2.3 选项与类型：向后兼容

`SatoriOptions` 从 0.26 到 0.63 **只增不减**：

| 选项                                                                                                                                  | 0.26 | 0.63           |
| ------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------------- |
| `fonts` / `embedFont` / `debug` / `graphemeImages` / `loadAdditionalAsset` / `tailwindConfig` / `onNodeDetected` / `pointScaleFactor` | 有   | 有（签名不变） |
| `onStyleError`（无效声明不再抛错，改为回调）                                                                                          | —    | **新增**       |
| `convertColors`（`oklch()`/`lab()`/`color-mix()` 转 `rgb()`，默认 `true`）                                                            | —    | **新增**       |

`index.d.ts` 依旧 `import 'react'`，`@types/react` 仍是必需（本站已装 19.2.18，与版本无关）。`satori(element, options)` 的入参仍是 `ReactNode`，**「不用 JSX、直接传 `{type, props}` 普通对象」在 0.63.2 的 README 里仍是官方写法**，本站的模板写法不需要改类型结构。

### 2.4 字体格式

0.26 README：「支持 TTF、OTF、WOFF，**不支持 WOFF2**」；0.63 README：「支持 TTF、OTF、WOFF、**WOFF2**」，并注明可变字体按默认实例渲染。

本站从 Google Fonts 拿到的是 TTF 静态字体（400/700 各一份、各约 10.5 MB），落在两个版本的交集内，**不需要动字体获取逻辑**。顺带一提：如果以后想省流量，0.63 允许把 `format('truetype')` 换成 WOFF2，但那是可选项，不是升级前提。

## 3. 隔离安装

```
npm install satori@0.63.2 --ignore-scripts    → added 22 packages in 12s
```

- 没有原生编译、没有 postinstall 拉二进制：`harfbuzzjs` 是 wasm、`fflate` 是纯 JS，`ignore-scripts` 不影响。
- 主项目 `package.json` / `pnpm-lock.yaml` **未被改动**（`git status` 全程为空），0.26.0 仍是 `node_modules/satori` 的实际版本。

**一处操作陷阱（Task 16 的原始命令会静默失败）**：计划里写的是在 `output/satori-upgrade/probe/` 里 `pnpm install`。实测 **pnpm 会把该目录当成父工作区的一部分**（根有 `pnpm-workspace.yaml`），报 `Done in 8.4s` 但**不生成 `node_modules`、不写 lockfile**，看起来成功、实际什么都没装。改用 `npm install` 才真正落地。后续若写实施步骤，这一条要写死在命令里。

## 4. 全量渲染：默认写法就错版

33 篇非草稿文章（34 个目录，1 篇 `draft: true`），同一份数据、同一份字体，两个版本各渲一遍。

**结果：0.63.2 也是 33/33 成功**，没有任何报错，`-webkit-box` + `lineClamp` 这类写法没有被判为无效样式（`onStyleError` 没触发，因为默认就是抛错，抛了就渲染不出来了）。但出图全错。

### 4.1 根容器盒模型：1200×630 → 1320×750

模板根容器是 `width: 100%; height: 100%; padding: 60px`。两版的实际盒：

| 写法                                        | 0.26.0   | 0.63.2       |
| ------------------------------------------- | -------- | ------------ |
| `width:100% height:100% padding:60`（现状） | 1200×630 | **1320×750** |
| 同上 + `boxSizing: "border-box"`            | 1200×630 | **1200×630** |
| `width:1200px height:630px padding:60`      | 1200×630 | **1320×750** |
| 同上 + `boxSizing: "border-box"`            | 1200×630 | **1200×630** |

0.26 对 padding 的处理等价于 border-box；0.63.2 改成标准 content-box（`width` 只算内容区，padding 外扩）。多出来的 120 = 2×60，正好是左右/上下 padding。

后果是**底部整行掉出画布**：最末节点 y 从 `520..570` 变成 `640..690`，而 viewBox 只有 630 高，PNG 里直接消失。这不是「差几个像素」，是每张图少一条信息。

### 4.2 绿色竖条被压窄：10px → 3px

标题行是 `[竖条 10×68] + [标题 marginLeft:25px]` 的 flex 行。标题自身是 `-webkit-box` + `lineClamp:3`，其 max-content 在这条标题上约 1052px；竖条 10 + 外边距 25 + 标题 1052 = 1087，超过 1080 的可用宽度 7px。

以 `20260831000000` 实测（`--all-nodes` 取全部节点盒）：

| 配置                   | 可用宽度 | 竖条宽 | 标题 left | 标题宽 |
| ---------------------- | -------- | ------ | --------- | ------ |
| 0.26.0                 | 1080     | 10     | 95        | 1045   |
| 0.63.2 默认（根 1320） | 1200     | **4**  | 89        | 1171   |
| 0.63.2 + `boxSizing`   | 1080     | **3**  | 88        | 1052   |
| 0.63.2 + 两处          | 1080     | 10     | 95        | 1045   |

机制一致：溢出多少，0.26 从标题扣，0.63.2 从竖条扣（默认 6px、修好根容器后 7px，差值来自可用宽度不同）。竖条被压到 3–4px，视觉上从一根绿柱变成一条细线，同时标题多出同等宽度，进而改变断行。给竖条加 `flexShrink: 0` 即完全复原。

### 4.3 两处改动一起上，几何复原

`boxSizing: "border-box"`（根容器）+ `flexShrink: 0`（竖条），全 33 张重渲：

| 指标                    | 未改         | 只补 boxSizing | 两处都补        |
| ----------------------- | ------------ | -------------- | --------------- |
| 单张平均差（0–255）     | 8.14–39.04   | 0.62–24.18     | **0.48–13.90**  |
| 差异像素占比            | 5.71%–24.02% | 0.98%–15.29%   | **0.71%–9.95%** |
| 全站均值（33 张平均差） | 22.77        | 8.16           | **3.93**        |
| 画布尺寸                | 1320×750     | 1200×630       | 1200×630        |

## 5. 几何复原后的剩余差异

### 5.1 文本度量漂移 ±0.9%

同一串文本、同一字体、同一字号，两版量到的自然宽度：

| 文本                                   | 0.26.0 | 0.63.2 | 差     |
| -------------------------------------- | ------ | ------ | ------ |
| `Windows 上的本地项目控制面：`         | 1001   | 1000   | −0.10% |
| `Windy Project Manager 的`             | 858    | 854    | −0.47% |
| `Windy Project Manager 的 Tauri`       | 1050   | 1041   | −0.86% |
| `Tauri 架构、离线扫描与可携带数据设计` | 1200   | 1207   | +0.58% |
| `从一个真实运行中的 Tauri 项目出发`    | 477    | 474    | −0.63% |

**方向不定、量级 <1%**，属于 HarfBuzz 整形与字距计算的正常漂移。它本身看不见，但它决定**换行边界**：上面第三条 1041 恰好小于可用的 1045，于是「Tauri」被塞进第二行；0.26 那边是 1050 > 1045，只能断在「的」后面。这是一条逐张验证过的个案；其余重排是否都出于同一机制，没有逐张复现，只能说量级与形态一致。

### 5.2 到底多少张变了

用逐行墨迹的横向分布相关性判定（换行一变，相关性立刻塌下来；纯亚像素位移仍在 0.99 以上）：

| 分组                       | 篇数 | 最低相关均值 |
| -------------------------- | ---- | ------------ |
| 明显重排（最低相关 <0.85） | 16   | 0.549        |
| 轻微位移（0.85–0.95）      | 5    | 0.920        |
| 逐行内容一致（≥0.95）      | 12   | 0.996        |

「逐行内容一致」那 12 张里还夹着 1 张**内容一致但整体位移**的（`20260320000000`，相关 0.973、下移 10px），它靠相关性分不出来，是靠逐张看差异图才发现的，见 5.4。

差异最大的 6 张（相关性用来区分「换行」与「位移」两种性质）：

| 文件             | 平均差（0–255） | 差异像素占比 | 最低行相关 | 性质                        |
| ---------------- | --------------- | ------------ | ---------- | --------------------------- |
| `20260831000000` | 13.90           | 9.95%        | 0.165      | 换行                        |
| `20260320000000` | 10.62           | 6.20%        | 0.973      | **整体下移 10px**（见 5.4） |
| `20261022192826` | 9.77            | 7.24%        | 0.318      | 换行                        |
| `20261002071103` | 9.31            | 7.09%        | 0.455      | 换行                        |
| `20260919135000` | 7.46            | 6.01%        | 0.489      | 换行                        |
| `20261002093931` | 6.98            | 5.72%        | 0.525      | 换行                        |

以 `20260831000000`（长标题）为例，肉眼可见的差别是：

- 旧版：第二行到「…Manager 的」结束，第三行「Tauri 架构、离线扫描与可携带数…」**被截断**
- 新版：第二行到「…Manager 的 Tauri」结束，第三行「架构、离线扫描与可携带数据设计」**完整放下**

也就是说新版的换行**通常更宽松**（同宽放下更多字），视觉结果偏向「少截断」。这属于观感变化，好坏需要站长看实际图判断，不是纯技术问题。

### 5.3 截断与省略号仍然有效

专门用一段 60+ 字的超长标题验证三行截断：

- 0.26：三行，末行末尾是**被裁掉一半的字形**
- 0.63.2：三行，末行末尾是规整的 `…`

`display:-webkit-box` + `lineClamp` + `textOverflow: ellipsis` 在 0.63.2 下仍然生效，且省略号处理更接近浏览器（对应 release 0.47.1 的 `Only keep a character before an ellipsis at the start of a line`）。**截断能力没有退化**。

### 5.4 无描述的那一篇整体下移 10px

`20260320000000` 是全站唯一没有 `description` 的文章。它的标题块在 0.26 里落在 `y=217`，在 0.63.2 里落在 `y=227`——**高度都是 164、逐行相关 0.973，只是整体低了 10px**。

原因是那个空串子节点：`description` 经 schema 默认后是 `""`，`description && {...}` 得到 `""`，children 变成 `[标题行, ""]`。0.26 把它算作一个占位子节点，`gap: 20px` 因此生效两次；0.63.2 直接忽略它，内容总高少 20px，`justifyContent: center` 于是把内容往下推 10px。

**这一条没有「两边都无操作」的写法**：无论改成 `description ? {...} : null` 还是保留空串，总有一个版本会偏移 10px。要么接受这 10px，要么在实施时把它算作一次预期内的视觉变化并单独说明。

## 6. 关键性质：两处改动在 0.26.0 上是无操作

用 0.26.0 跑「原样」与「两处都补」两遍，逐像素比对：

```
共同文件 33 / 最大单通道差 0 / 平均差 0 / 差异像素 0 / PNG 字节数完全相同
```

**逐字节一致**。这意味着模板改动可以独立于版本升级先落地：先给根容器加 `boxSizing: "border-box"`、给竖条加 `flexShrink: 0`，用现有 0.26 重新构建，产物不变，风险为零；把这些改动和依赖升级拆成两个提交，升级那一批就只剩版本号与锁文件。

同理，`clamp` 与 `flexShrink` 的验证也说明这两处不是「为 0.63 打补丁」，而是**本来就该写的显式声明**——只是 0.26 的默认值恰好等价，掩盖了缺失。

## 7. 性能与体积

| 项                          | 0.26.0  | 0.63.2  |
| --------------------------- | ------- | ------- |
| 仅 satori 的耗时（中位/张） | 9 ms    | 8 ms    |
| 首张（含 wasm 冷启动）      | 160 ms  | 202 ms  |
| 33 张 satori 累计           | 464 ms  | 458 ms  |
| SVG 总量                    | 3522 KB | 3409 KB |
| PNG 总量                    | 2029 KB | 2024 KB |
| 包体（解压）                | 5.4 MB  | 26 MB   |

单张耗时**两版相当**：同一批跑两次，中位数在 7–9 ms 之间来回摆，累计差 6 ms 属噪声，不能当结论。真正稳定可复现的只有两项：首张多 42 ms 的 wasm 冷启动（一次性），以及 `node_modules` 从 5.4 MB 涨到 26 MB。

整条链路里 PNG 编码（sharp）占大头，每张 35–50 ms，是 satori 本身的 4–6 倍。**构建期增量可忽略**，真正的代价是依赖体积与首次加载。

## 8. 没有验证的部分（写清边界）

这一轮只做隔离环境取证，下面这些**没有跑**，实施时才会遇到：

- **真实构建链**：`astro build` 里 33 个 `getStaticPaths` 并发/串行调用 satori 的表现、内存峰值、与 sharp 的协同，都没测。探针是单进程串行。
- **字体拉取失败降级**：站点在 Google Fonts 拉不到时会传空 `fonts` 数组。0.63.2 下空字体渲染不报错（已验证最小例子），但中文必然是空白，与 0.26 是否一致没逐张验证。
- **CI（Linux）上的产物一致性**：探针只在本机 Windows / Node 22.22.2 上跑。0.63.2 的布局是 wasm 浮点运算，跨平台末位差异虽未测，但按 Tailwind 那轮的经验，**不能假设逐字节相同**。
- **OG 图的线上缓存**：`Cache-Control: max-age=31536000, immutable`，文件名带内容哈希吗？没有——路径是 `/og/<slug>.png`。升级后旧缓存不会自动失效，这是既有问题，不在本轮范围。
- **`embedFont` / `graphemeImages` / `loadAdditionalAsset`**：本站都没用，未验证。

## 9. 三种走向的判断依据（不做决定）

README 要求三选一，这里只摆证据：

| 走向                 | 支持证据                                                                   | 反对证据                                                       |
| -------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------- |
| **值得排期**         | 装得上、33/33 出图、两处一行改动即复原几何、截断能力未退化、构建耗时无差别 | 16/33 张标题换行点改变 + 1 张下移 10px，观感变化需要人工逐张过 |
| **需先改模板**       | 两处改动明确且极小；且在 0.26 上是逐字节无操作，可先行落地                 | 真正的「需改」只有这两处，谈不上「需要重新设计模板」           |
| **保留 0.26.0 冻结** | 无书面依据的风险依旧存在；升级收益目前看只有「跟上上游」                   | 0.26.0 已 7 个多月未更新，且无 CHANGELOG 意味着以后更难追      |

一个尚未被回答、但会影响判断的问题：**OG 图是给搜索引擎和社交平台抓的缩略图，这 17 张的排版变化是否值得为此付出升级成本**。这是产品判断，不是技术结论，本报告不给建议。
