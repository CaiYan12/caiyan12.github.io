## Problem Statement

主站的样式层绑在 Tailwind CSS 3.4.19 上。这个版本已经停止演进，而站点仍在持续演进（新增了 Nice Books 独立壳、多个组件与大量自定义样式）。继续停在 v3 会让两件事持续付出代价。

**第一，接入方式本身是一条硬约束，且它正在拖累每次样式改动。** Tailwind v3 是 PostCSS 插件，接入靠仓库根的一个 PostCSS 配置；配置靠一个 CommonJS 文件，被 `@layer` 包裹的样式块靠 Tailwind 自己的构建期指令展开。这套机制有一个已被实测确认的副作用：**`@layer` 块里的纯 CSS 类名会被当成 utility 候选，按 content 扫描结果 purge 掉**。本站已有 15 条规则因此从产物里消失（侧栏小部件、标签云、幻灯片三组，均为 Emlog Colorful 迁移遗留的死类）。这类丢失是静默的：没有报错、没有构建警告，规则只是在产物里不见了。

**第二，样式覆盖关系的推理规则即将失效。** 仓库里有一条被写进构建文档、供后续所有会话依赖的承重结论：「Tailwind v3 的 `@layer` 是构建期指令，产物里根本不存在 `@layer`，冲突按『特异性 → 源顺序』判定」。它对 v3 成立（实测产物内 `@layer` 计数为 0）。但 Tailwind v4 引入了**真实的 CSS 级联层**，这条结论不再成立，而**依赖它做出的样式决策会开始错**。本次迁移实测已经撞上这个问题的实体：typography 插件的 `.prose` 规则落在 `utilities` 层，压过站点 `components` 层的 28 条正文规则（正文标题 24px→36px、段落 14px→16px、链接品牌绿变插件蓝且失去下划线、全部 margin 归零）；提高特异性的四种方案**全部无效**，因为层序压过特异性。

**第三，站长的要求是「不产生任何意料之外的变动」。** 当前 UI 与设计是长期磨合的产物，每一处视觉都有理由。迁移若引入任何非预期变化，都是净损失。因此本次迁移的验收标准不是「构建通过」，而是「**线上渲染不发生可见改变**」。

## Solution

把 Tailwind 从 3.4.19 升到 4.3.4，并把接入方式从 PostCSS 插件改为官方 Vite 插件；配置保留现有 JavaScript 配置文件并显式加载，不迁到 CSS-first 主题块；**把站点的样式规则从 `@layer` 里移出**，让它们以层外身份参与级联，从而精确还原 v3 靠「特异性 + 源顺序」得到的结果；补齐四处因 v4 语义变化而必须显式声明的补偿；同步所有承重文档，并写下一条 ADR 记录这套接入方式与被否掉的替代方案。

迁移完成后：站点的样式层不再绑在一个停止演进的版本上；那条关于 `@layer` 的承重结论被替换成符合 v4 语义的新结论；样式覆盖关系重新变成「可推理的」——因为站点规则恒胜，覆盖顺序由源文件顺序唯一确定，不再需要在层序与特异性之间做心算。

## Implementation Decisions

### 接入方式

- Tailwind 升到 4.3.4，改由官方 Vite 插件接管，接入点放在构建配置里既有 Vite 插件列表的首位。
- 原 PostCSS 配置保留，但只承担两件事：CSS 嵌套处理与厂商前缀。
- **CSS 嵌套处理是必需项而非冗余**：主样式文件里有 8 处**不带 `&` 符号的隐式嵌套**（拉绳壁纸挂件的绳与衣身 SVG 子规则），没有嵌套处理器时这些规则是非法 CSS 会被整条丢弃。
- **嵌套插件的来源变了**：v3 时它是 tailwindcss 包内附带的子路径，v4 的包不再导出该路径（构建直接报错），故改为显式依赖独立的嵌套处理包。
- 厂商前缀处理**保留**：v4 内置的前缀处理器与既有 autoprefixer 的浏览器目标集不同（前者硬编码、不读 browserslist 配置；后者读 browserslist，而本仓库没有该配置故走其默认集）。实测本站自有规则在两条链下声明值零差异，但前缀集合不同——保留是为了维持既有产物的前缀行为不变。

### 配置加载

- **保留现有 JavaScript Tailwind 配置文件**，用 v4 的 `@config` 指令显式加载，不迁到 CSS-first 的 `@theme` 块。
- 理由（实测）：纯 CSS-first 主题块会**丢失全部自定义色板工具类**（含 Nice Books 的纸墨色板与品牌色）；且站内自定义阴影 token 写成 `var()` 自引用时，浏览器判定无效 → 阴影变成无。
- 代价（已核实）：v4 下 `theme.extend` 的值**不生成对应的 CSS 变量**，工具类直接内联值。本站全站零处引用这类变量，因此无损。
- 两套样式入口各自独立加载配置，两处相对路径深度不同。

### 源码扫描范围

- **扫描范围必须包含 TypeScript 与 JavaScript**：Nice Books 的渲染构造器与交互脚本在 **TS 模板字符串**里拼装工具类；漏掉 TypeScript 会**静默**丢失若干工具类（实测丢 5 个，产物小 4.3KB，零报错零警告）。
- 保留 Markdown 在扫描范围内（本站 Markdown 内无工具类，保留仅为与既有配置一致）。

### 层语义与样式规则归属（核心决策）

- **把站点样式规则的 `@layer` 包裹去掉**，让它们以层外身份参与级联。
- 原理：CSS 级联规范规定层外的普通声明排在所有层内普通声明之后，因此站点规则恒胜，**精确还原 v3 靠「特异性 + 源顺序」得到的结果**。
- **只改层序声明是不够的**：站点有一条层外的元素级重置规则，它依然优先于任何层内规则。实测「把组件层改名并显式声明层序」只把可见回归从 21 项降到 17 项，正文标题的 4 项全坏。
- **提高特异性一律无效**：实测四种方案（加后代选择器、改用 `:where`、改用 `:is`、提升父级特异性）全部仍是同一结果。层序压过特异性。
- **代价**：站点规则恒胜意味着它们也压过 Tailwind 工具类，与 v3 的语义相反（v3 里工具类排在组件层之后）。已核实全站无「站点类名与工具类撞名」，但这是需要持续守住的边界。
- 两套样式入口各自解包。

### 四处显式补偿

四处都是 v4 语义变化导致的、**若不显式写死就会静默变化**的项：

1. **正文链接的下划线**：v3 靠 typography 插件的规则胜出；v4 的层序让层外的「链接无下划线」规则排到最后。显式写死下划线。
2. **正文列表项的左缩进**：v3 的缩进来自 typography 插件的 `.prose :where(ul > li){padding-inline-start:.375em}`（**补记（2026-11-04 实施时纠正）**：本条原先写「浏览器默认的内边距、实测 5.25px」，取错了基准——真实来源是插件那条 em 相对值，正文 13px 下实测计算值 **4.875px**）；v4 的预检把内边距归零。显式复刻同一个 em 相对值。
3. **表单控件的白底**：v3 的预检给表单控件设白底；v4 改为透明，而站内搜索框自身没有背景声明，会在浅灰页面底上露出底色。显式补白底；自带背景的控件由各自规则覆盖，不受影响。
4. **一处装饰符号的行高**：v4 把字号工具类的行高从**绝对长度**改成**比值**，继承到使用 em 相对字号的子元素时会按子元素字号重算（20px→17px），混排行盒少 1px，导致书库页文档高度变化 1px、其后内容整体上移。显式写绝对行高。
    - **不能用 `inherit` 修**：继承的是比值不是计算值，实测无效。
    - 影响面已清点：全站使用 em 相对字号任意值的仅两处，其中仅这一处的父级是带比值行高的字号工具类；另一处父级是无单位数行高，两版行为一致。

### 死样式的处理

- 站点样式表里有 15 条规则在 v3 产物中不存在——它们的类名在源码中**零引用**（迁移遗留的死类）。v3 丢弃它们是因为把层内类名当工具类候选并按扫描结果 purge；移出层后 v3 也保留，v4 本就不 purge。
- 迁移到 v4 本身即达成「死样式不再被丢」这个目标；**额外在 v3 侧补齐的价值仅在于让两个版本的产物集合一致**，最终产物上会被 v4 覆盖掉。
- 处置方式：把这批死类一并移出层，使两版产物集合一致（v3 与 v4 各提交一次，合并推送）。

### 产物集合与死类核实

- 全量规则集合 diff：v3 约 2000 条 / v4 约 2080 条；「只在 v4」约 120 条、「只在 v3」约 22 条。
- 「只在 v4」这批里既有**死类补回**（已核实零引用），也有**v4 新语义产生的工具类**（important 后缀语法、space 系列的新选择器、group 变体、预检的表单重置）——后者是 v4 的正常产物，不是回归。
- 「只在 v3」这批经核实是**提取方法的偏差**（选择器被合并导致误判），实际存在。其中 `.tw`、`.backtop`、`:root` 三条经逐条核实确实在 v3 产物里，且两版计算值零差异。

### 文档与决策记录

- 改写构建文档里关于 `@layer` 语义的那条承重结论：从「v3 的 `@layer` 是构建期指令」改为「v4 起是真实级联层，站点规则必须移出层」，并附实测证据与被否方案。
- 改写样式文档里「构建链插件顺序」那条（插件集合变了）与「正文行内代码」那条（层语义推理方式变了）。
- 在命令文档里新增一条「样式 A/B 的判据纪律」，收纳本轮踩出的坑。
- 变更日志新增一条。
- README 的待办区里 Tailwind 那一项从「进行中」改为已完成，并写明关键机制与踩坑。
- **新写一条 ADR**，记录「保留 JS 配置 + 移出所有层」这两个决定：难回退、有真实取舍（与官方推荐方向不同）、且令人意外（提高特异性无效、层序声明不够）。

## Testing Decisions

一个好测试只断言**外部可观察行为**：真实渲染后的计算值与几何、真实交互后的结果状态、可访问性属性。不断言内部实现细节、不断言 CSS 源文本、不用固定毫秒等待动画相位。

**贯穿全局的验收判据：可见差异为零。** 任何影响渲染的计算值变化（尺寸、字号、字重、行高、颜色、背景、边框宽度、间距、位置、显示方式、文本装饰、列表样式、对齐、换行）都算失败；**边框宽度为零时的边框颜色变化不计入**——颜色不渲染。

这是本轮实测确立的判据形式。原始差异条目数并不等于可见差异：一次实测的 462 条差异条目里，308 条是边框颜色变化（元素边框宽度为零，不渲染）、152 条是产物里绝对地址带了不同端口号（归一化后完全相同）、2 条是采集时刻图片尚未加载完成导致的瞬时高度差（重测即归零）。**真正需要关注的差异为零**，但要看出来这一点，必须先做两步归一化——端口归一化与可见性判定。缺了任何一步，都会被上万个无意义的条目淹没。

### 缝隙一：样式指纹 A/B（复用既有工具）

- 被测对象：两个版本的构建产物在同一批真实页面上采集的计算样式指纹。
- 复用仓库既有的样式指纹采集与比对工具与页面清单模块（13 页带壳真页面 + 10 页扩展页面 = 23 页，含首页、文章页、列表页、相册页、独立壳页与 404 页），不新增采集脚本、不新增页面清单。
- 覆盖判据：23 页逐页比对；差异属性分类统计；**所有有可见边框的元素，其边框宽度与颜色逐条相同**；关键元素（导航项、正文标题、正文链接、行内代码、输入框、页面盒模型）的计算值在两版间完全一致；**文档高度逐页相同**。
- 先例：仓库既有的样式指纹工具已示范该形态——判据落在计算值与几何上，采集期归一化随机 id、比对期归一化主机地址与切页瞬态类名。
- **需要的一处微调**：地址归一化目前只认 `localhost:<端口>`，不认 `127.0.0.1:<端口>`；两个版本用不同端口提供服务时会产出上万个全是端口号的假差异。须补上 `127.0.0.1` 形式。

### 缝隙二：真实浏览器交互冒烟（复用既有工具）

- 被测对象：构建产物在本地预览服务下的真实交互与计算样式。
- 复用仓库既有的浏览器冒烟台（122 条判据）与页面清单模块，遵守其签名约定与「放行清单必须写在调用点」的纪律；基址按既有形态约定传入站点根且不带结尾斜杠。
- 覆盖判据：导航项的间距与高度；正文标题字号与字重；正文链接颜色与下划线；行内代码字号与断行行为；输入框背景色；**可点元素的光标负扫**（凡可见的可点元素，计算光标须含本站手型光标资源）；页面主要区块的盒模型与文档高度。
- 先例：既有的主站 UI 冒烟已示范该形态，且已有一条手型光标负扫（变异验证过：把某两处裸 `pointer` 改回后该条立刻翻红并报出具体处数）。

### 缝隙三：构建链门禁（复用既有链路）

- 被测对象：完整构建链。
- 复用既有的构建脚本链（它已内含 KaTeX 类名判据、佛祖横幅注入、Pagefind 索引生成），不新增 workflow 步骤。
- 覆盖判据：构建成功且页面数与升级前一致；KaTeX 类名判据通过；Pagefind 索引正常产出。
- 先例：KaTeX 批次已把「产物 HTML 里的旧类名出现次数必须为零」接进构建链，作为同类静默失败的机械化守卫。

### 缝隙四：类型与格式（复用既有命令）

- 被测对象：类型检查与格式门禁。
- 复用既有的类型检查命令与 Prettier 检查命令（范围含源码、文档与仓库根 Markdown）。
- 覆盖判据：类型检查零错误零警告；Prettier 全绿。
- 先例：既有 CI 的 lint 流程即这两条。

### 缝隙五：样式单元测试的格式依赖（复用既有测试）

- 被测对象：Nice Books 的样式单元测试。
- 该测试用「缩进两级的大括号」作为媒体查询块的结束标记；站点规则移出层后，格式化把块内缩进从四级改成两级，该正则会匹配到块内某条规则的收尾而非块尾，断言随之失配——**而 CSS 规则本身完全正确**。
- 覆盖判据：修正块尾匹配后全部样式单元测试通过。
- **这条是本次迁移实际踩到并修掉的**：它说明「测试红但规则看着没错」要先怀疑断言对格式的依赖。须把这条写进命令文档。

### 缝隙六：截图对比（复用既有方法，不作为门禁）

- 用法：对关键页面在桌面与移动两个视口下各拍两张全页截图，逐像素比对；**但必须先量噪声底线**，否则数字没有判据力。
- 噪声来源有两类，必须区分：**运行时随机**（背景壁纸从四张候选里随机选一张，覆盖整页，是最大来源）与**构建期随机**（侧栏一组文章在构建期随机挑选）。
- 噪底线要用**同一版本的两份独立构建**来量（同一份产物连拍两次会低估，因为后者的随机内容来自同一份产物）。
- 排除运行时随机背景层后，多数页面的两版差异降到与噪声同量级；超出噪声的项，其差异像素经 DOM 复核全部落在边框宽度为零的元素上。

## Out of Scope

- **不迁移到 CSS-first 的 `@theme` 主题块**。已实测它会丢失全部自定义色板工具类，且自定义阴影 token 写成 `var()` 会自引用失效。CSS-first 化作为独立后续项单独排期。
- **不删除那 15 条死样式**。本次只把它们移出层使两版产物集合一致，不做清理。清理属于另一件事（它们是 Emlog Colorful 迁移遗留）。
- **不动 Nice Books 的纸墨色板与字体槽位定义**，也不把它迁成独立项目（那是站长的另一项计划）。
- **不删除 `books.css` 里那条隐藏语义补偿规则**。它在 v4 下变冗余，但该模块将来独立成项目时，那条规则正是它脱离主站预检后的护栏。
- **不给站点的字号工具类补浏览器下限相关的 fallback**。本站已在用 `color-mix()` 且全是无 fallback 写法，本次不扩大范围。
- **不改 `tailwind.config.cjs` 里的任何 token 定义**（颜色、字体、阴影、圆角一律照搬）。
- **不改任何站点的 HTML 结构或类名**。唯一的类名改动是给一处装饰符号补行高工具类。
- **不动 Satori 的升级**。那是另一项独立工作（上游无变更日志，需先做隔离探针）。
- **不引入新的运行时依赖**。新增的嵌套处理包是构建期依赖。
- **不新增常驻回归门禁脚本**。四条显式补偿与「规则不得落回层内」靠既有缝隙与文档守护，不新增构建期断言脚本。

## Further Notes

- **浏览器下限是这次迁移唯一的产品级取舍**：v4 要求 Safari 16.4+ / Chrome 111+ / Firefox 128+，且该目标集是硬编码的、不读 browserslist 配置。站点已在用 `color-mix()`（14 处，无 fallback 写法），老浏览器里整条声明失效而非仅功能缺失。本次接受该下限——它比同批 Mermaid 迁移接受的 Safari 17.4+ 更宽松，且老 iOS 设备本就拿不到 Safari 大版本更新。
- **「移出所有层」会让站点规则恒胜**，这是与 v3 语义相反的方向，也是本规格最需要长期守住的一条。文档里已写明：新增样式时不必再担心构建期丢弃，但也别指望用工具类覆盖站点类。
- **两笔提交一次推送**：第一笔让死类在 v3 下也保留（两版产物集合一致），第二笔是 v4 迁移本身。分开提交是为了回退时能分辨是哪一层引起的变化；因为一次推送，线上只会看到最终态。
- **回退路径**：迁移的全部改动（依赖、接入方式、两套入口、层解包、四处补偿、文档）在同一笔提交里，回退即回退一笔。第二笔（v4 迁移）可单独 revert 回 v3 + 死类补齐的状态。
- **部署身份判定仍用平台无关证据**：样式资源名、页面可见文本、响应头的最后修改时间。**不要用 JS chunk 哈希或 Pagefind 索引哈希判定部署身份**——两者平台相关，Windows 与 Linux 构建必然不同，本仓库历史上已因此差点误判两次。
- **本轮的验收证据是一次性的**，不入库；随后的常驻判据才是入库的。证据目录在被忽略的输出目录下。
- **构建链的联网前提**：构建前需设置相应环境变量，否则 OG 图端点拉字体会失败（表现为「没有加载任何字体」的错误，与本次迁移无关）。
