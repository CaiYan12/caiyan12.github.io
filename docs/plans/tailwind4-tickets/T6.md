## What to build

对迁移做最终验收，并在验收通过后推送上线。

验收的标准是**站长的原始要求**：当前 UI 与设计是长期磨合的产物，迁移不得产生任何意料之外的变动。因此验收不是「构建通过」，而是「访客看得见的渲染结果与迁移前一致」。

三条证据链并行：

1. **计算样式指纹**：23 页逐页采集两个版本的产物并比对，可见差异必须为零。
2. **真实浏览器**：在桌面与移动两个视口下拍全页截图逐像素比对。这里有个必须先做的前提——**必须先量噪声底线**，否则数字没有判据力；且要区分两类随机源：背景壁纸是**运行时**随机（从四张候选里随机选一张，覆盖整页，是最大来源），侧栏一组文章是**构建期**随机。噪底线要用同一版本的两份独立构建来量（同一份产物连拍两次会低估）。
3. **关键交互**：导航项布局、正文标题、正文链接、行内代码、输入框、可点元素的光标负扫、页面盒模型与文档高度，逐项与迁移前一致。

推送上线后，用**平台无关证据**确认部署身份：样式资源名、页面可见文本、响应头的最后修改时间。**不要用 JS chunk 哈希或 Pagefind 索引哈希判定部署身份**——两者平台相关，Windows 与 Linux 构建必然不同，本仓库历史上已因此差点误判两次。

上线后还要跑既有的线上验收脚本。注意线上验收要连跑三次：部署刚完成时第一次可能因 CDN 或模块未就绪而报红，第二、三次才稳定——只跑一次会得出错误结论。

## Acceptance criteria

- [x] 23 页计算样式指纹比对：**可见差异条目数为零**（边框宽度为零时的边框颜色变化不计入）
- [x] 桌面与移动两个视口下，全页截图的差异与构建间噪声同量级；超出噪声的项逐条归因到「不渲染的差异」
- [x] 关键交互逐项与迁移前一致；可点元素的光标负扫零异常
- [x] 完整构建链通过（含既有的产物类名判据、Pagefind 索引生成）；类型检查零错误零警告；Prettier 全绿
- [x] 线上验收脚本连跑三次，三次均通过（`pnpm verify:live` 三次均 29/29；`pnpm verify:live:swup` document 级接管通过）
- [x] 部署身份用平台无关证据确认（样式资源名、页面可见文本、响应头最后修改时间）
- [x] 推送前确认全部改动已落在分支上，且没有夹带无关改动
- [x] 推送后更新待办区状态与变更日志的发布记录
