## 附近天气胶囊（wttr.in 单源，2026-09-29 上线）

- **天气是侧栏的子元件，只有两处界面**：主站侧栏**首位**（`sidebarConfig.widgets` 的 `weather` 排在 `blogger` 之前）与 `/domain/` 终端天气行。数据契约 `public/weather/weather-service.js`，卡片渲染 `public/weather/sidebar-widget.js`，终端行 `public/domain/js/weather.js`。
- **唯一上游是 wttr.in**：浏览器定位（普通精度、`maximumAge: 0`、8 秒）→ 坐标粗化到一位小数 → GET `https://wttr.in/<lat>,<lon>?format=j1&lang=zh`。天气请求上限同为 **8 秒**（双源时代的 12 秒已随和风一并收回）。**绝不按 IP 推断位置**，也不做定时刷新。整页刷新才重新定位；同一标签页内模块级会话只有一份，故 Swup 切页既不重复弹定位也不重复请求（天气只有侧栏一处挂载，2026-09-29 二次改判后手机挂载已撤除）；成功态刷新只重取天气。卡片在 swup 容器（`main`）内，切页后重绑**只走 `colorful:page:loaded`**（主题协议，同 `WidgetNewLog` / `Slideshow`），别再听 `astro:page-load`——那是 `docs/agents/components.md` 的「客户端脚本与 Swup 生命周期」一节禁止新代码使用的第四轨；脚本本身是 head 级 `data-swup-ignore-script`，切页不重新执行，首帧由模块末尾的直接调用负责，事件只负责新节点（`requestLocation()` 会同步把状态置为 `locating`，所以同一轮里的两次 `pageReady()` 弹不出第二次定位）。`/domain/` 保持终端版式、成功态无刷新按钮、失败才有 `[重试]`；无 JS 时留静态说明，不得残留「天气加载中…」。
- 和风天气试验**已搁置**（2026-09-29 站长裁决）；其代理实现的留档目录已于 2026-10-07 经复议**删除**（依据：活代码零引用、重启素材已缺前端半边、目录净效应只剩一条门禁 advisory）。完整留档在 git 历史，入库点 `4c8482b`（`git show 4c8482b:docs/history/weather-qweather-proxy/README.md` 可取回搁置理由、已验证边界、配额账本终值与重启五步）；Q1–Q62 决策访谈全文仍在 `docs/history/qweather-settingup-history-sessions.md`。`lang=zh-cn` 实测对 149 仍返回英文，所以本地码表不可省。
- 图标是 7 枚真资产 `public/weather/icons/{clear,cloud,overcast,rain,snow,storm,fog}.svg`，组件按 `weatherKind` 的返回 kind 换 `<img src>`（同时写 `data-weather-kind`；kind 单源在 service，见下条）。**平涂/分层、不用 `<linearGradient>`** 是风格约定（贴近天气 App 的实心字形）。注意原先记的理由「同页两枚挂载、渐变 id 会撞重复 id 负扫」**从当初就不成立**：这些 SVG 走 `<img src>` 加载，其内部 id 不进入宿主 DOM，`smoke:ui` 的重复 id 负扫根本看不见它们——何况手机第二枚挂载已于 2026-09-29 撤除。留规则、改理由，别拿这条去论证内联 SVG 也不行。`overcast`（阴）与 `cloud`（少云/多云，云后露日）必须分开——阴天画太阳是错的。
- **文字→kind 的分类规则已单源**（2026-10-07 结构加深 T3/T4）：唯一实现在 `weather-service.js` 的 `weatherKind(condition, code)`，经 `window.WeatherCapsule` 暴露——雷→storm、雪/雹/冰→snow、雾/霾→fog、雨→rain、晴/113→clear、阴→overcast、云→cloud、**无匹配→null**（终端回退 🌡️、侧栏回退 cloud，分叉由两侧 adapter 吸收，两侧输出与单源前逐项一致）。历史上那套 `/^2\d{2}$/→storm` 之类的**码段判定必错**：wttr 的 2xx 段同时含雷暴(200)、雪(227/230)、雾(248/260)、冻毛毛雨(263–284)，实测把三条判错。分类矩阵由 `scripts/weather-rules.test.mjs` 的 12 例锁定（含「小雨夹雪」雪先于雨、表外码「雨雾」雾先于雨两个优先级钉子）；侧栏冒烟只守呈现层（7 类各一页的图标/壁纸命中）。**粒度裁决仍然成立**：终端的 `weatherIcons` 是 47 码 → **9 枚** emoji 且码表优先（kind 映射只接表外码），侧栏是 **7 个** kind 对 7 个 svg 资产——两层粒度不同，合表要么让 `/domain/` 从 9 格掉到 7 格（访客可见），要么照抄 9→7 塌缩表（复杂度没少）；卡片**不吃码表**的效果也保留（`weatherKind` 只吃文字与 113）。坐标粗化与定位/天气文案同样单源在 service（`roundCoordinates` 数字对/null 单一契约、`locationErrorMessage` 等四个文案函数），侧栏 `sidebar-widget.js` 自 T4 起是纯 adapter。
- 码表 `weatherNames` / `weatherIcons` 内容对齐**上游 wttr.in 官方简中表**（`chubin/wttr.in` 的 `share/translations/zh-cn/conditions.txt`，46 码，核对于 2026-09-29）+ 本站自译 `149 烟霾`，共 47 码且两表键集合必须一致。覆盖由 `scripts/weather-codes.test.mjs` 逐码锁住（缺码、译名漂移、掉默认 🌡️ 都会翻红）；上游加码时人工比对并同步那张测试里的 `UPSTREAM_CODES`。表外码的回退是「英文原文 + 🌡️」，属可观测降级。
- **窄屏不渲染天气卡，也不许为它初始化**：`#sidebar` 在 `≤768px` 只是 `display: none`、节点仍在 DOM 里，所以 `sidebar-widget.js` 的 `pageReady()` 先用 `sidebarIsRendered()`（对 `card.closest("#sidebar")` 取计算样式）过滤挂载点，否则手机访客会为一张永不显示的卡被弹定位授权、并发出一条永远看不见的天气请求 —— 这比视觉上违和更糟。撤除的是 `MainGridLayout.astro` 的 `.mobile-weather-slot` 挂载与 `global.css` 里它的两条规则；`#content` 里从此不再有天气节点，文章卡 `nth-child` 色带自然不受影响。
- 标题栏必须走 `WidgetLayout.astro` 的 `icon` prop（现用 `fa-cloud`），它自带 `.widget > .icon` 的 47×30 盒、`border-right 1px #dadada` 分割线与 `#fbfbfb` 底——**不要另写头部样式或为此下载新图标**。
- 卡片内所有外部数据文本（城市、天气描述、状态文案）**一律 `white-space: nowrap` + `text-overflow: ellipsis` + `title` 兜底**，不许改回 `overflow-wrap`（换行会撑高卡片）。实测四组极端值 × 两档视口卡片主体高度恒 113.2px、零横向溢出（2026-10-26 复测；此前记的 114.9px 是 2026-09-29 壁纸上线前的旧值，壁纸那笔把主体改矮了 1.7px）。加进元信息行的新文案要先量它与同行邻居的总宽——旧数据态那句曾被截掉 126px，正解是缩短文案而不是放宽布局。
- **胶囊高度已预留，加载/失败态不再塌陷**（2026-10-26 站长裁定）：`.weather-widget-body` 带 `min-height: 113.2px`（= 成功态实测主体高；该元素计算值已是 border-box，故不裁切内容）+ `align-content: center`。此前「定位中 / 定位失败 / 天气失败无旧数据 / 无 JS」四态只有一行状态文字，主体实测只有 32.9–59.1px，**把下方元件整体上移 54–80px**；现在五态等高。**成功态与旧数据态版式一位不变**（满数据变体的内容恰好填满：113.2 = 8+9 padding + 5 gap + 75.27 读数 + 15.94 页脚）。**但预留高度锚的是「满数据」变体**（体感/风速/湿度三格齐全，也就是上游的真实响应形态）：上游三个字段缺失时参数行整行隐藏、读数行只剩 54.27px，那种变体本来就装不满，内容会在预留区里垂直居中——**这是有意的，不是死空白**。**居中只作用于无数据态**，圈定条件用 `:not([data-weather-kind])`——该属性只在拿到天气数据时才存在（成功态与旧数据态都有，旧数据态照常画壁纸），故这两态完全不受影响。无数据态的状态文字与重试按钮**水平 + 垂直都居中**（失败文案过长时靠 `max-width: 100%` 仍走 ellipsis 截断，不得撑破卡片）。判据在 `scripts/sidebar-weather-smoke.mjs`：五态等高、成功态 == 113.2px、满数据成功态内容恰好填满、缺参数行时内容不溢出且上下留白对称、状态迁移后下方元件顶边一位不动。**改胶囊版式（padding / 行高 / 参数行）必须同步复核这五条**，否则预留高度会与实际版式脱钩。
- **加载期转圈（2026-10-26 站长裁定）**：卡内大转圈是**自绘 SVG** `<svg class="weather-widget__spinner" viewBox="0 0 48 48" width="48" height="48" aria-hidden="true" focusable="false">` + 内一枚 `<circle>`（`src/components/widget/WidgetWeather.astro`）。几何：**环心半径 22.5、线宽 3px、开口 120°**（落在 12 点到 3 点之间即右上象限；圆周 2πr = 141.37 → `stroke-dasharray="94.25 47.12"`、`stroke-linecap="round"`、`stroke="currentColor"`）。**为什么自绘而不用 FA4 的 `fa-circle-o-notch`**：那枚字形的线宽/直径比是给 14px 小图标设计的，放大到 48px 后线显得过粗、开口偏小；且字形版盒子会在 FA 字体未加载时被回退字体度量撑到约 61px（会随字体加载跳动），自绘由 svg 的 width/height 定死 **48×48**、无此不确定性。**别改回字形**。尺寸 48px、浅灰 `#999`（**非 token** —— 站内已有该字面量，站长裁决取此值；不为一个只有一处用处的颜色去动 `:root`；环用 `currentColor` 取色，改 CSS 里那一处即可）。**旋转复用站内既有的 `@keyframes colorful-spin`**（1s linear infinite），不新写关键帧。**显隐一律走 CSS 的 `data-weather-state`，JS 不参与**：只在「正在加载、且卡内尚无数据」时出现 —— `locating`（等定位）与 `weather-loading`（首次天气请求在飞）；状态机里那个 `loading`（「正在读取天气」）是**同步被 `weather-loading` 覆盖**的（定位回调里 set loading → renderAll → `fetchWeather()` 同步 set weather-loading → 再 renderAll，两次渲染同在一个任务内），**浏览器来不及画它**，别按它写判据或样式。成功 / 旧数据 / 错误 / 无 JS 态一律不出现转圈。**手动刷新（已有数据）时卡内读数照旧，改由标题栏刷新图标自转** —— 刷新按钮在 actions 槽、是 body 的兄弟，故用 `.widget:has(.weather-widget-body[data-weather-state="weather-loading"][data-weather-kind]) .weather-widget__refresh svg` 取状态（`transform-box: fill-box` + `transform-origin: center` 让它绕字形自身中心转；`transform-box` 是站内首次使用）。**高度预算：48 + 14（5px 网格 gap + 9px 外距）+ 15.94 = 77.94 ≤ 内容盒 96.2**，故主体仍为 113.2px；**转圈不得做到 66px 以上**，否则卡片被撑高、下方元件重新开始跳。**若把转圈换回 FA 字形**，所有针对它的 CSS 声明必须用 `.weather-widget__spinner.fa` 复合类提特异性 —— vendored `font-awesome.css` 排在 `global.css` 之后（产物实测 `.fa{}`@169652 > `.weather-widget-body{}`@126666），而 `.fa{display:inline-block; font-size:inherit}` 与普通类同为 (0,1,0)，写普通类会被压掉（转圈缩成继承字号、且 `display:none` 失效）。`prefers-reduced-motion` 下转圈停转（保留静态圆环）、刷新图标停转，信息由 `role=status` 的状态文字承担。判据在 `scripts/sidebar-weather-smoke.mjs`：转圈显隐（正反双向）、确实在转（按 `getAnimations()` 的 running 状态判定，不用 sleep）、尺寸 48×48 + 线宽 3px + 浅灰、刷新图标自转、reduced-motion 不转、六态等高（新增「读取天气中」）。
- **中文地名由本地目录解析，绝不直接显示 wttr 的 `areaName`。** 实测 80 个中国坐标返回 80 个互不相同的**村镇级**拉丁站名（深圳→`Dills Corner`、佛山→`Tainan`、南昌→`Nanchangfu`、上海→`Bailianjing`），既不是访客所在城市，也永远是英文。两层规则（`public/weather/weather-service.js` 的 `resolveCityName`）：① 坐标在中国 bbox 内且距某地级市中心 ≤**120km** → 用官方中文市名；② 境内但半径外 → 用 wttr 自带的 `region` 经 35 行省表译成中文省名；③ 境外 → 保持 `areaName` 原名。**绝不拿 `areaName` 当省表键**（"Beijing" 这类村镇名撞上省名就是错标，实测会串），省表兜底只认 `country`（港澳 `region` 为空、只有 `country` 认得）。**省表查表必须 `Object.hasOwn(provinceNames, key)`**：`key` 直接取自上游 JSON，朴素查表 `provinceNames[key]` 会把 `"__proto__"` / `"constructor"` 当成命中并返回原型对象，卡片于是渲染出 `[object Object]`（`textContent`，无 XSS 面，但是垃圾值）。2026-09-30 由评审提出并补守卫，用例锁在 `scripts/weather-city-catalog.test.mjs`（对抗性 `region` 必须落回 `areaName`）。可推广的一般规矩：**客户端里凡用网络字段做对象键，先 `hasOwn`**；数字键（如 `weatherIcons[Number(code)]`、`/domain/` 的 `messages[error.code]`）撞不到原型键，不需要这层守卫。
- 城市目录 `public/weather/city-catalog.js`（**生成文件、随仓库跟踪、不参与 `pnpm build`**）：367 个地级市与直辖市的 `[中文名, 纬度, 经度]`，坐标 1 位小数，8.2KB / gzip 3.8KB。数据源是阿里 DataV 行政区划图集 `geo.datav.aliyun.com/areas_v3/bound/<adcode>_full.json`，取 `properties.level === "city"` 的 `name` + `center`。再生成：`pnpm build:weather-cities`（显式运行，需网络）。名字归一在 `scripts/build-weather-cities.mjs` 的 `shortName()`：先砍 `自治州|自治县|地区|盟|林区|市` 后缀，再从第一个民族标记处截断（`伊犁哈萨克自治州`→`伊犁`、`德宏傣族景颇族自治州`→`德宏`、`西双版纳傣族自治州`→`西双版纳`），归一后撞名就退回全名（`海南藏族自治州` 与 `海南省`）。**不要用 GeoNames 替代**：它按聚落收录，市辖区各自成条（浦东/宝安/樊城 离坐标更近）、历史名混在别名里（迪化）、繁简不分（衡陽），调人口门槛治不好，实测命中率只有 74–89%。
- 目录必须在服务之前加载，且**两个壳各自都要挂**：`src/layouts/Layout.astro`（主站）与 `src/domain.html`（`/domain/` 是独立壳、不走 Layout）都要有 `<script src="/weather/city-catalog.js" defer>` 排在 `weather-service.js` 之前。漏掉 domain 那一处，终端天气行会退回英文（实测过）。
- 侧栏卡片的城市行**不带**「附近：」前缀（卡片标题已经是「附近天气」，行内重复白占 39px；侧栏那一列可用宽度实测 112px，最长拉丁名 `Zhangjiagang` 需 85px，去前缀后不截断）。`/domain/` 终端行**保留**前缀，因为那里没有标题承载语义。
- 覆盖门：`scripts/weather-city-catalog.test.mjs`（11 项，已串入 `pnpm test:weather`）锁「目录逐行纯中文且落在中国范围内」「11 个大市逐个点名核对」「半径外落省名（敦煌→甘肃）」「境外保持原名（伦敦/东京）」「目录缺失时降级不抛错」「`Shanxi`≠`Shaanxi`」「对抗性 `region`（`__proto__` 等）必须落回 `areaName`」，并把 **2026-09-29 实测到的 32 个 `region` 取值**当作「API 返回范围」逐个要求必须译出——wttr 改写法时这条会翻红。三道变异验证均实测会红（删目录里的「南昌」、删省表的 `Nei Mongol`、把省表查回朴素 `provinceNames[key]`）。
- **卡片内部版式（2026-09-29 retro-tuning 定稿）**：主视觉行是「图标 + （温度上、天气状态下）」成一组、地名单独贴右缘（`align-self: start` 再加 `padding-top: 9px`，让地名与大数字读作同一水平线，而不是浮在右上角）；其下是**通栏参数行** `体感 32° │ 风速 11 km/h │ 湿度 75%`，每格是「图标 + `__detail-label`(11px 弱) + `__detail-value`(12px/500 强)」，第 2、3 格靠 `border-left 1px #e6e6e6` 分隔；截断落在 `__detail-value` 上（`min-width:0` + `overflow:hidden` + `ellipsis` + `nowrap`），标签是站内固定文案不参与截断；页脚是**组件状态栏** `数据：wttr.in 15:15`（时间不再带「获取于」，它与来源之间的可见间距是 `.weather-widget__time` 的 `margin-left: 5px`，**不是文本空格** —— 判据若按文本写必须容忍 innerText 在行内元素间补的空格）。层级只靠字号/字重/对齐/间距，不靠颜色。实测：卡片 253×113.2px，六档视口高度恒定、零横向溢出、参数行从不截断。
- **参数行的列宽必须是「内容定宽 + 两端铺满」，不是等宽**：`grid-auto-columns: minmax(0,auto)` + `justify-content: space-between`。等宽三格在加图标后不成立——实测每格 77.7px、去掉内距只有 63.7px 可用，而「图标+风速+`11 km/h`」需要 86px，`1fr` 会把单位截成 `11 k…`；三格按内容共需 249px > 行宽 233px，所以还得把格内内距 7→5、gap 3→2、图标 11→10 才装得下（现况：三格 `truncated:false`、`deadRight 0`）。「风」这个标签也已按站主意思改成「风速」，两字标签是容量被压扁的直接原因之一。
- **量「有没有铺满」绝不能用 `scrollWidth > clientWidth`**：不溢出的块级元素两者恒等，这个比值永远报「零空洞」，上一版就是用它把参数行右侧真实的 48.8px 死区（占行宽 21%）读成了 0。正确度量是**最后一格右缘到行右缘的距离**（`row.right - lastCell.right ≤ 1`），且截断要用**注入超长值**验证真的咬得住（断言值元素 `scrollWidth > clientWidth`、计算值为 `ellipsis`、且行的宽高一位都不许变）。
