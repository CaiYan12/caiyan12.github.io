# 0016：可画判定由第一个信号定案，`decode()` 只等不判

## 背景

拉绳壁纸有两条独立事务：**预载**在独立图像对象上确认候选可用，**提交**把新地址落到原图层再等它画出来。两条事务各自散落着同一套结算知识——什么时候问 `decode()`、什么时候算可画、什么时候只结算一次、结算之后清什么。这套知识因此在两个文件里各写了一遍，晚到事件与清理规则也跟着写两遍，改一处忘另一处就会出现「迟到的 `load` 把已经定案的结局翻掉」这类只在弱网下偶发的回归。

两条事务的结算口径本来还不一样：预载要等 `decode()` 落定才结算（比 `load` 晚一个微任务），提交在 `load` 处理器里同步结算。同一件事有两种时延，测试也就有了两种时序假设。

## 决定

**一、抽出 `whenPaintable(image, { timeoutMs })`，只此一个 interface。** 返回 `"ok" | "failed" | "timeout"` 三档，没有 mode、没有回调、没有回滚标志。

**二、第一个信号定案。** `load` 与 `error` 谁先到谁说了算，后到的不翻案。

**三、可画与否在 `load` 当刻取快照**（`complete && naturalWidth > 0`），不推迟到 `decode()` 落定之后。要判的是「这张图此刻能不能画」，不是「等解码落定后那张图还剩什么」——后者会被后来的信号改写。

**四、`decode()` 只用来等解码落定，不用它的结果。** 兑现与被拒走同一条判定：加载完成不等于解码完成，弱网下不等待会画出半截；但 `decode()` 被拒**不算失败**——并发解码与大尺寸图片会拒掉合法图片。

**五、结算即清理，且只做一次。** 清计时器，摘掉自己挂的两个监听。用 `addEventListener` 而不是 `onload` 属性：提交侧操作的是长期共享的原图层，属性赋值会占掉别人的处理器槽位。

**六、超时独立成档。** 12s（预载）与 1.5s（提交）的预算、`decode()` 的提问位置、失败要不要回滚、谁写 `src`，全部留在调用方。

**七、已经可画就早退**，不再等信号。对预载是空操作（每次都是全新对象，`src` 未写前不可能 `complete`），对提交是必需（`decode()` 被拒时 `load` 可能早已到过，不会再有第二个 `load`）。

## 被否掉的方案及理由

**用「`decode()` 成功」当可画判据。** 否掉：会拒掉合法图片，spec 明确写了并发解码导致拒绝的情形。这是旧提交侧与旧预载都没有明说的分歧点——两边其实都按尺寸兜底，只是没写成同一条规则。

**把 `timeout` 并进 `failed`。** 否掉：预载要靠它区分「换下一个候选」与「网络彻底不通」，证据需求不同。

**两条事务合成一条。** 否掉：回滚语义、超时含义、证据需求都不同，合并只会把这些差异塞进参数。

**module 带 mode / 回滚标志。** 否掉：那等于把两条事务的差异搬进 module，只是换个地方写两遍。deletion test 要过的是「这个 interface 有没有比它替换掉的代码更窄」，不是「有没有把两边都装进去」。

**结算后保留监听，用 `settled` 吞掉迟到信号。** 否掉：那是一条永远悬挂的处理器。

## 代价与边界

- **一处语义变化**：S10 场景（`load` 后同一 tick 到达 `error`）预载侧从 `failed` 变 `ok`。真实 Chromium 里量了三次——合法图只收到 `load`、坏图只收到 `error`、只有换 `src` 才会同时收到两个；预载的图像对象每次新建、`src` 只写一次，因此**实测不可达**。即便发生，`ok` 也更贴近事实：那张图确实加载成功且有固有尺寸。
- **提交侧多问一次 `decode()`**（同一元素同一 `src`，Chromium 实测第二次为 0ms、结果不变）。这是为了不改既有断言的取舍，不是漏看。
- **第二次 `decode()` 很慢时会超时回滚**（S9）。实测 0ms，保留该场景是为把风险边界写死，不是认为它会发生。
- **module 不判断「该不该换图」**：候选轮换、忙碌锁、失败播报、减少动态都留在调用方，module 不知道壁纸的存在。

## 守卫在哪

- **早退那条不能删。** 对预载像死代码，删了会在提交侧分叉。
- **`claimed` 与 `settled` 分工不同**：`claimed` 决定结局，`settled` 保证结算的副作用也只做一次。只删 `settled` **不改变任何结局**（Promise 只能 resolve 一次，`claimed` 已经挡住迟到信号），所以判据必须能数「一共摘过几个监听器」才看得见——这条是本轮补的。
- **别把 `decode()` 的兑现值传进 `settle()`。** 它的结果不参与判定，只用于等。
