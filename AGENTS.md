## Coding Rule:

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:

- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

- 版本：astro 6.4.8 / @astrojs/react 5.0.7 / @astrojs/svelte 8.1.2 / astro-expressive-code 0.43.1（`^0.43` 而非 0.44）/ @swup/astro 1.8.0（**实际安装 1.8.0，但 `package.json` 的范围仍声明 `^1.7.0`**——本条按 Q45-B 记录该差异而不是顺手改范围：pnpm lockfile 里存的是 specifier，改 `package.json` 不改 lock 会让 CI 的 `pnpm install --frozen-lockfile` 直接失败；要改得连 lock 一起改并实测） / tailwindcss 3.4.x。**Tailwind 不再经 @astrojs/tailwind**——该集成 peer 只到 Astro 5，是当初升级的硬阻碍；现由根 `postcss.config.mjs` 直连 `[tailwindcss/nesting, tailwindcss, autoprefixer]`，顺序照集成原先的实际产出，`autoprefixer` 已转为直接依赖。原配置文件里 import 的 `postcss-import` 既非声明依赖、全站 CSS 又零 `@import`，会让该文件在集成内静默加载失败，已移除；**不要再加回 @astrojs/tailwind**。
- **Tailwind v3 的 `@layer` 是构建期指令，不是 CSS 级联层——产物里根本不存在 `@layer`**（实测：`dist` 内九个 css 文件 `grep -c '@layer'` 全为 0）。因此源码里的 `@layer base/components/utilities` 只影响"被展开到何处"，**冲突一律按「特异性 → 源顺序」判定**，不存在"无层规则胜过 @layer"这种级联层语义。本仓库两处历史结论曾据此误判：① 根字号 `html{font-size:13px}`（写在层内）失效的真因是它被更靠后源顺序的同特异性 `html{font-size:100%}` 压掉，而非层序；② 行内代码 `.prose code{font-size:13px}` 被描述成"关在 `@media (max-width:680px)` 内、桌面永不生效"，实际它在 `@layer components` 内、桌面一直生效，压住它的是另一条规则的更高特异性。推断样式覆盖关系时请直接量计算值，别按层语义推理。
- **Markdown 处理器已迁到 `markdown.processor: unified({...})`（2026-09-20，构建告警已清零）**：Astro 6.4.0 起提供 `processor`，且它的默认值本就是 `unified()`，所以这一步只是把插件从「隐式默认 + 事后折叠」改成显式声明，`git diff -w` 只剩 import 与包裹两行。要点：① `@astrojs/markdown-remark` 必须作为直接依赖并**精确对齐 astro 自己解析到的版本**——astro 6.4.8 的 package.json 里是硬钉 `7.2.0`（不是范围），装 latest 7.3.1 不会去重、会变成两份副本；② 旧的 `markdown.remarkPlugins` 由 `core/config/validate.js` 的 `coerceLegacyMarkdownPlugins` 在 **resolveConfig 内部** push 进 `processor.options`，而 `build()` 是先 resolveConfig 再跑集成钩子，所以 expressive-code 的 `rehypePlugins.push(rehypeExpressiveCode)` 在两条路径下都排在我们插件**之后**，顺序不变；③ `gfm`/`smartypants` 在 7.2.0 内有 `processor.options.gfm ?? shared.gfm` 兜底，本站未设置。**改 markdown 管线的 A/B 验收方法（下次直接复用）**：两侧都用 `pnpm exec astro build`（绕开 fetch 脚本以保证输入相同）并先删 `node_modules/.astro/` 与 `.astro/data-store.json`；`dist/_astro/**` 全部资源应逐字节相同（最强信号）；HTML 侧必须先剥掉 `<div class="widget tab-widget" data-tab-widget>`（侧栏「文章推荐」含构建期随机挑选），否则每次构建都有约 122 个页面的假性差异；用 `--import` 预加载去改 `Math.random` **消不掉**这层噪声（Astro 的 markdown 渲染跑在 worker 线程里，预加载只在主线程生效，实测无效）。要把噪声归零做全量证明：把 `src/utils/shuffle.ts` 的 `shuffleArray` 临时改成原样返回，两侧都跑 `astro build` + `inject-buddha-banner` + `pagefind`，再比对完整产物（本次结果：1114 个文件逐字节 0 差异，含 pagefind 索引）。（升级当时另有比对：三篇文章正文 HTML 与 Astro 5 完全一致，含 73KB 的 Markdown 语法示例文。）
- `getTagList()` / `getCategoryList()` **必须保持全序**（文章数倒序 → 最早引入该标签/分类的文章时间 → 名称）。原因：并列名次若只靠 `Array.prototype.sort` 的稳定性，顺序取决于 `getCollection()` 的遍历顺序，而 Astro 5 与 6 定义不同——升级实测会让侧栏标签云 32 个药丸重排，并连带改变 `.blogtags` 的 nth-child 六色轮换归属。任何新增的"按计数排序"列表同理。
- `src/constants/*.json` 与 `src/data/site-stats.json` 的排版由 `scripts/lib/write-json.mjs` 的 `formatJson()` 在生产端保证（`JSON.stringify(x, null, 制表符)` 再过一遍 Prettier），七个产物幂等、`prettier --check ./src` 覆盖它们。旧写法下六个 constants 用同一种序列化，四个只是碰巧没有短数组才合规 —— 短数组（如 `"variants": [480, 720, 1080, 1440]`）会被 Prettier 折行而 `JSON.stringify` 每行一个元素，这正是 `image-manifest.json` / `github-projects.json` 当初被塞进 `.prettierignore` 的原因。**新增写 JSON 产物的脚本请走同一个写入器，别再往 `.prettierignore` 加行**；该文件现在只剩 vendored 的 `src/styles/font-awesome.css` 一条。
- **deploy.yml 的 "Sync Giscus comments" 步骤跑在 `pnpm install` 之前**（`node scripts/sync-site-stats.mjs`，那时 `node_modules` 还不存在），所以这条链路上的脚本只能用 Node 内置模块。`formatJson()` 因此对 prettier 用 `try { await import("prettier") }` 延迟加载、缺失即回落到纯 tab 缩进 —— CI 那次写出的排版只留在 runner 工作区、不回提交，站点内容不受影响；本地装了 devDependencies 才是 Prettier 排版。给这条链路加任何包依赖都会让部署在 13 秒内以 `ERR_MODULE_NOT_FOUND` 失败（实测踩过）。
- 本地安装须带项目内 store：`pnpm add --store-dir .pnpm-store <pkg>`（`node_modules/.modules.yaml` 记录 `storeDir: <repo>/.pnpm-store/v10`，全局配置已不指向它，裸跑 add 会报 store 版本不匹配）。
- **依赖升级是人工决策，`.github/dependabot.yml` 把已钉死的包按名字整条 `ignore`（2026-10-01 立）**。原先的通配 `ignore` 只挡 `version-update:semver-major`，挡不住 0.x 包——实测 Dependabot 把 `satori 0.26.0→0.33.5`、`katex 0.16.47→0.18.9`、`astro-expressive-code 0.43.1→0.44.2` 全归进「minor」组提了 PR（expressive-code 那条还**改写了范围本身**：caret 在 0.x 上本就跨不过 minor，`^0.43.1` 被改成 `^0.44.2`）。于是名单内整条忽略：`astro`、`@astrojs/react`、`@astrojs/svelte`、`@astrojs/markdown-remark`、`astro-expressive-code` 与两个 `@expressive-code/plugin-*`、`satori`、`katex`、`@swup/astro`、`prettier`。**为什么必须人工看**：本仓库 CI 只有 `Astro Check` + `prettier --check ./src` + `Astro Build` 三件，约 250 条实机判据（`smoke:ui` 144／侧栏天气 68／`test:fancybox` 27／`domain-weather` 29／`test:weather` 29）**一条都不在 CI 里**，所以「PR 三项全绿」不构成升级依据。**`prettier` 尤其只能人工升**：3.9.6→3.9.9 会把行内 `$…$` 里的 `*` 当 emphasis 改写——24 篇文章逐篇双版本跑下来只有 `src/content/posts/20260320000000/index.md` 变化，13 行，形如 `$Q_2^*>Q_1^*$` → `$Q_2^_>Q_1^_$`，后者拿本项目 katex 直接喂 `renderToString` 实测抛 `KaTeX parse error: Expected group after '^'`（`Q_1^*=Q_1^u` → `Q_1^_=Q_1^u` 同错）。该篇有 764 个 `$`、35 处「行内公式里带 `*`」却只被改了 13 行，**触发条件在整篇解析态而不是某一行的写法**（单独取第 500 行、以及几种最小形状均复现不出来），所以别指望按 grep 定点修——**「CI 红了就跑 `pnpm format`」这条路会把已发布文章的公式打断**。`dompurify` 不在忽略名单里（它是精确钉的消毒边界，唯一使用点 `src/ai-news/components/ReaderView.tsx` 的 `DOMPurify.sanitize(article.contentHtml, …)`，安全补丁希望继续被提出来）。
- 升级回归验证脚本 `scripts/upgrade-style-audit.mjs`（Astro 6→7 时复用）：`capture` 用 Playwright 对 24 个关键页逐元素采集计算样式指纹（含 `::before/::after`），`diff` 支持顺序无关比对。采集前必须冻结动画、种子化 `Math.random`（否则稿纸逐字符抖动不可复现），并排除明月浩空播放器（远端异步、含 `#myhk*` 的 id 选择器，`[class*=]` 抓不到）、看板娘、轮播、3D 标签云、swup 瞬时类名与带端口的绝对 url——这些都是实测过的假阳性来源。**同数据的新旧构建 A/B 才是有效比对**；线上产物与本地基线必然存在差异（CI 会重新生成 GitHub 快照与贡献日历、幻灯片当前帧与播放器歌单属异步状态），不要拿线上比对当样式结论。配合 `Last-Modified` 与内容断言使用。`deploy.yml` 的 `cache: false` 仍不得回退。

### 配置驱动（改配置 = 改站点）

`src/config.ts` 是所有站点行为的控制中心：

- `siteConfig` — 标题、作者、URL、每页文章数、备案号等
- `navBarConfig` — 平铺导航项（首页/微言碎语/留言板）+ 四组下拉：`archiveSite`（文章归档：全部文章 `/archive/` + 标签分类 `/tag/` + 文章分类 `/category/` + 热门推荐 `/hot/`）、`aboutSite`、`extra`、`resourceSite`；`social`（B站/QQ/微信/RSS 图标）仍在 `Navbar.astro` 的 `.m-nav` 渲染；下拉渲染分列在 `Navbar.astro`（桌面 hover 下拉）与 `MMenu.astro`（移动端全屏菜单），**两处必须同步修改**，父项 current 由子链接 `some()` 判定
- `sidebarConfig` — 侧栏小部件顺序
- `commentConfig` — **Giscus 评论**，已开启并绑定 `CaiYan12/caiyan12.github.io` 的 `Announcements` 分类；文章评论区使用 `pathname`，留言板使用 `specific` + `data-term="guestbook"`；`reactionsEnabled: "1"`、`emitMetadata: "0"`；其余 `repoId`、`categoryId`、语言和主题 URL 在 `src/config.ts` 中维护
- `slideshowConfig` — 首页幻灯片（图片在 `public/images/slide/`）

### 内容组织

- 文章：`src/content/posts/<yyyymmddhhmmss>/index.md`（**目录名即 URL slug**，可放封面图在同目录），schema 在 `src/content.config.ts`（posts + spec 两个 collection）
- frontmatter 字段：title/published/category/tags/description/image/pinned/views/comments/hotness(0-5)/draft 等，其中 comments/hotness 用于首页吐槽与热门展示；views 为迁移兼容字段，当前不渲染围观数
- 文章页的分类/标签链接**只对真的生成出来的路由发**（`src/pages/posts/[...slug].astro`）：合法性判据与 `/tag/[tag]`、`/category/[category]` 的 `getStaticPaths` **同源**，即 `getTagList(publicPosts)`／`getCategoryList(publicPosts)` 的名字集合——这两个函数都先过 `isPublicPost`，所以 `private: true` 文章独占的那一项从不生成页面。无路由的项降为**纯文字 `<span>`**，不是整行删除：私有文章若用的是公开分类（实测 `技术` 就是有路由的），链接照常保留。勿改回无条件发 `<a>`，那会重新制造 404（GitHub issue #41）。冒烟 `pnpm smoke:ui` 的 `#41` 三项判据守着这条，**被检页面清单取自 sitemap** 而不是从站内链接爬——私有文章页不被任何公开页链出，爬是爬不到的。**将来若改 sitemap 收录策略，必须在同一笔 commit 里给那条判据换页面清单来源**，否则它会静默退化成「只查公开页」（spec #42 登记的跨轮硬约束）
- 特殊页面：`src/content/spec/about.md`（关于）
- 数据文件：`src/data/diary.ts`（说说）、`friends.json`（友链单一数据源）+ `friends.ts`（`Friend` 类型与兼容导出）、`comments.ts`（开发环境最新评论 mock）、`guestbook.ts`（开发环境留言板单条换一批 mock）、`site-stats.json`（构建期同步快照）
- 相册：**文件夹驱动**——`public/images/albums/<相册名>/` 下放图即自动生成相册（`src/utils/album-scanner.ts` 构建期扫描，中文目录名没问题，slug 用原始名不要预编码）

### 文章 URL 硬规则（必须遵守）

- `src/content/posts/` 的所有直接子目录（公开、私密、草稿、模板示例均包括）必须严格匹配 `^\d{14}$`，格式为 `yyyymmddhhmmss`。
- 文章路由固定为 `/posts/<yyyymmddhhmmss>/`；禁止使用标题、中文或其他自定义目录名作为 slug。
- `published` 只有日期时，时间部分统一补 `000000`；已有时分秒必须与目录名保持对应，不得用文件系统时间替代。
- 新文章使用 `pnpm new-post -- <yyyymmddhhmmss> [标题]`；`scripts/validate-post-slugs.mjs` 已接入 `pnpm build`，目录不合规时构建必须失败。
- 整理旧文章目录后，必须同步检查 README、CHANGELOG、文章正文示例及其他静态引用中的旧 `/posts/.../` 路径。

### 客户端脚本与 Swup 生命周期

- `src/utils/theme-script.ts` 是唯一的客户端逻辑中枢：导航高亮、返回顶部、双击回顶、移动端菜单、Fancybox/KaTeX 初始化
- **Swup 重初始化协议（2026-09-06 审查后统一，新增客户端代码必须遵守）**：`main` Swup 容器内的组件统一监听自定义事件 `colorful:page:loaded`（切换后重跑）并配 `dataset` 守卫防重复初始化（如 Slideshow 的 `data-initialized`）；`main` 容器外的布局级组件（导航/移动菜单/返回顶部/背景）只随 `pagefindReady()` 初始化一次，靠 `*Bound` 旗帜或 dataset 守卫防重入，勿自行监听 `astro:*` 原生事件——容器外布局级确需 before-swap 清理（如 Fancybox destroy）才允许直接听 `astro:*`。历史上四轨并存（_Bound 委托/dataset 守卫/自定义事件/内联 astro:_），新代码不得新增第四种形态；theme-script 按"唯一协议 + 多 init 函数"保持单文件，按关注面拆分为远期独立一期（2026-09-06 审查决策）
- **Swup 切换页面时组件脚本不会重跑**，所以需要重绑定的东西（Fancybox、导航高亮）都注册在 `initSwupHooks()` 的 `content:replace`/`page:view` 里；新增交互若依赖新页面 DOM，必须加到这两个 hook 中
- **`updateHead` 按环境分叉（`astro.config.mjs`，2026-09-20）**：dev 传 `{ persistAssets: true }`、生产保持 `true`。Vite 在 dev 下把懒加载的第三方 CSS（fancybox、katex）以运行时注入的 `<style>` 挂进 head，swup 的 head 同步按"新页面没有此节点"把它删掉，而模块已在 Vite 图里、不会再注入一次，于是客户端切页后灯箱与公式失去样式（灯箱容器从视口尺寸塌成文档高度，首页→文章→点图必现）。**勿改成 `updateHead: false`**（会连带停掉 title/meta 同步），**也不要把 `persistAssets` 带进生产**——生产各页 CSS 是独立 `<link>`，必须照常增删以免跨页样式泄漏。dev 判定用 `process.argv` 含 `dev`（Astro 6 的 `defineConfig` 只接受对象，无 `({ command })` 函数形态）。
- **SwupScriptsPlugin 重建的是整个 document 的 script，不只 swup 容器**（`reloadScripts` 默认 true，scope 为 `head`+`body`）：常驻容器外的第三方经典脚本每次切页都会被 `replaceWith` 重新执行——myhkw 播放器的 `jquery.min.js` 与 `/api/player/` 因此抛 `明月浩空音乐播放器已加载，禁止重复添加！`。这类"元素在容器外、本就不必重跑"的脚本必须显式标 `data-swup-ignore-script`（插件选择器 `script:not([data-swup-ignore-script])`），`Layout.astro` 的两个播放器脚本已加；勿凭"它在 `main` 之外"推断不会被重跑。
- 导航高亮 `syncNavHighlight()`：逐锚点 toggle 时**跳过 `javascript:void(0)` 锚点**（下拉父项按钮，永不匹配），下拉父项与 MMenu 分组的 current 由其子链接 `some()` 统一计算——直接加载（`pagefindReady`）与 `astro:after-swap`（Swup 不替换 `main` 外的导航）都会重算；勿回退为逐锚点裸 toggle，否则构建期写入的下拉父项 current 每次加载都会被抹掉。路由前缀匹配连带效果：/tag/xxx/ 与 /category/xxx/ 页上"文章归档"下拉及"标签分类"/"文章分类"子项呈 current（语义正确，保留）
- 头部微言轮播（`#header .text`，2026-09-05 重写）：机制复刻原版 AutoScroll（limh.me `global-pjax.js`）——`theme-script.ts` 的 `initHeaderTicker()` 每 4s 将 ul 上滚一条（0.8s ease），`transitionend` 后把首条 li 移到末尾实现无限轮转（无克隆条，任意条数无缝，条数取 `diary.slice(0, 4)`），hover 暂停、移出恢复，`prefers-reduced-motion` 不启动，dataset 守卫防定时器叠加（原版 pjax 重复加载会叠加，勿学）。**节奏 4s/条 = 停留 3.2s + 滑动 0.8s 对齐迁移前 CSS 关键帧版手感，勿改回原版 300ms**（2026-09-05 用户确认）；步长 `-24px` 与 global.css `#header .text li` 行高耦合，改行高须同步。头部在 Swup 容器外，随 `pagefindReady()` 初始化一次即可，勿加进 after-swap hook。**实现只有这一条**：主容器文本块 `#header .text` + `initHeaderTicker()`。曾并存的 CSS-only 死块 `.header-ticker` + `@keyframes ticker-scroll`（含窄屏副本）从未被任何标记或脚本引用，已于 2026-09-22 删除——不要再把它当「缺 `prefers-reduced-motion` 配对的活跃动画」上报
- **微言轮播链接「无悬停视觉反馈」是既定设计（2026-09-23 裁决，勿重开）**：`#header .text a{color:#fff}`（`src/styles/global.css`，选择器锚点，行号约 1957）以 id 特异性 (1,1,1) 压掉通用 `a:hover{color:var(--colorful-green)}`（约 1770 行，(0,1,1)），且 `#header .text` 全族没有任何 `:hover` 的 `text-decoration` 规则，于是头部那 4 条 `<a href="/diary/">` 悬停时**既不变色也不出线**。站长判定**保持无反馈**：不要补下划线、不要换色、不要给它加 `::after` 线条（补它属于新增视觉行为，须重新过裁决）。**这条 id 规则是承重结构**——删它或降它的特异性等于悄悄给头部开启绿色 hover，动通用 `a:hover` 前必须先想清楚这点。两件事**不在**本次「无 hover」的范围内、也不得顺手删除：hover 暂停滚动（`initHeaderTicker()`，纯 JS 行为）与 `:focus-visible` 描边（键盘可达性）。回归由缝隙 A 承担（`pnpm smoke:ui` 用 `hoverProbe()` 取静息/悬停计算值，断言 `color` 与 `text-decoration-line` 差值为零）——**缝隙 B 的采集排除表显式含 `#header .text` 整族，对它必然零漂移，不能当验过了**；该判据属「锁现状」型，落地即绿，其红证据由变异验证提供。

### 侧栏“最新评论”换一批交互硬约束

- “换一批”必须提供可感知的加载状态：切换期间显示加载图标动画与“加载中…”文案，设置 `aria-busy="true"` 并禁用按钮，防止重复点击。
- 切换完成、异常或空数据时必须恢复默认图标/文案、`aria-busy="false"` 与可用状态；不得让按钮永久停留在加载中。
- 加载动画仅作用于“换一批”操作图标，必须遵守 `prefers-reduced-motion: reduce`；不得恢复最新评论头像的旋转效果。
- “换一批”只能操作构建期嵌入的评论数据，客户端不得新增 GitHub/Giscus 请求或其他评论数据依赖。

- **唯一上游是 wttr.in**：浏览器定位（普通精度、`maximumAge: 0`、8 秒）→ 坐标粗化到一位小数 → GET `https://wttr.in/<lat>,<lon>?format=j1&lang=zh`。天气请求上限同为 **8 秒**（双源时代的 12 秒已随和风一并收回）。**绝不按 IP 推断位置**，也不做定时刷新。整页刷新才重新定位；同一标签页内模块级会话只有一份，故 Swup 切页既不重复弹定位也不重复请求（天气只有侧栏一处挂载，2026-09-29 二次改判后手机挂载已撤除）；成功态刷新只重取天气。卡片在 swup 容器（`main`）内，切页后重绑**只走 `colorful:page:loaded`**（主题协议，同 `WidgetNewLog` / `Slideshow`），别再听 `astro:page-load`——那是「客户端脚本与 Swup 生命周期」一节禁止新代码使用的第四轨；脚本本身是 head 级 `data-swup-ignore-script`，切页不重新执行，首帧由模块末尾的直接调用负责，事件只负责新节点（`requestLocation()` 会同步把状态置为 `locating`，所以同一轮里的两次 `pageReady()` 弹不出第二次定位）。`/domain/` 保持终端版式、成功态无刷新按钮、失败才有 `[重试]`；无 JS 时留静态说明，不得残留「天气加载中…」。
- 和风天气试验**已搁置**（2026-09-29 站长裁决）：代理实现整份留档在 `docs/history/weather-qweather-proxy/`（含搁置理由、已验证边界、配额账本终值、重启五步），不参与构建与测试。`lang=zh-cn` 实测对 149 仍返回英文，所以本地码表不可省。
- 图标是 7 枚真资产 `public/weather/icons/{clear,cloud,overcast,rain,snow,storm,fog}.svg`，组件按 `iconKind` 换 `<img src>`（同时写 `data-weather-kind`）。**平涂/分层、不用 `<linearGradient>`** 是风格约定（贴近天气 App 的实心字形）。注意原先记的理由「同页两枚挂载、渐变 id 会撞重复 id 负扫」**从当初就不成立**：这些 SVG 走 `<img src>` 加载，其内部 id 不进入宿主 DOM，`smoke:ui` 的重复 id 负扫根本看不见它们——何况手机第二枚挂载已于 2026-09-29 撤除。留规则、改理由，别拿这条去论证内联 SVG 也不行。`overcast`（阴）与 `cloud`（少云/多云，云后露日）必须分开——阴天画太阳是错的。
- `iconKind` **只按中文天气文字判定**（雷→storm、雪/雹/冰→snow、雾/霾→fog、雨→rain、晴/113→clear、阴→overcast、其余→cloud）。历史上那套 `/^2\d{2}$/→storm` 之类的**码段判定必错**：wttr 的 2xx 段同时含雷暴(200)、雪(227/230)、雾(248/260)、冻毛毛雨(263–284)，实测把三条判错。**这条优先级清单在两处各写一份**（卡片的 `iconKind` 与服务层表外码的 emoji 回退 `conditionIcon`），2026-09-30 之前两边顺序并不一致（服务层把 雨 排在 雾/霾 前），已按上面这个书写顺序对齐，并**两边各补一条用例锁死**：服务层在 `scripts/weather-service.test.mjs`，卡片在 `scripts/sidebar-weather-smoke.mjs` 的逐码归类判据（现 12 例，最后一例是表外码 999 + `lang_zh`「雨雾」→ `fog`）。**不要把两份合成一张表**：服务的 `weatherIcons` 是 47 码 → **9 枚** emoji，卡片是 **7 个** kind 对 7 个资产，粒度不同；合成要么让 `/domain/` 从 9 格掉到 7 格（访客可见），要么照抄一张 9→7 塌缩表（复杂度没少）。而且两边首要依据相反——服务层先查码表、命中就不进级联，卡片**故意不吃码表**（正是上面那条裁决的理由），下沉等于把卡片改成码驱动。真实的重叠命名已经在跑：码 317 的中文是「小雨夹雪」，两边都把 雪 排在 雨 前 → `snow` ✓。
- 码表 `weatherNames` / `weatherIcons` 内容对齐**上游 wttr.in 官方简中表**（`chubin/wttr.in` 的 `share/translations/zh-cn/conditions.txt`，46 码，核对于 2026-09-29）+ 本站自译 `149 烟霾`，共 47 码且两表键集合必须一致。覆盖由 `scripts/weather-codes.test.mjs` 逐码锁住（缺码、译名漂移、掉默认 🌡️ 都会翻红）；上游加码时人工比对并同步那张测试里的 `UPSTREAM_CODES`。表外码的回退是「英文原文 + 🌡️」，属可观测降级。

- **中文地名由本地目录解析，绝不直接显示 wttr 的 `areaName`。** 实测 80 个中国坐标返回 80 个互不相同的**村镇级**拉丁站名（深圳→`Dills Corner`、佛山→`Tainan`、南昌→`Nanchangfu`、上海→`Bailianjing`），既不是访客所在城市，也永远是英文。两层规则（`public/weather/weather-service.js` 的 `resolveCityName`）：① 坐标在中国 bbox 内且距某地级市中心 ≤**120km** → 用官方中文市名；② 境内但半径外 → 用 wttr 自带的 `region` 经 35 行省表译成中文省名；③ 境外 → 保持 `areaName` 原名。**绝不拿 `areaName` 当省表键**（"Beijing" 这类村镇名撞上省名就是错标，实测会串），省表兜底只认 `country`（港澳 `region` 为空、只有 `country` 认得）。**省表查表必须 `Object.hasOwn(provinceNames, key)`**：`key` 直接取自上游 JSON，朴素查表 `provinceNames[key]` 会把 `"__proto__"` / `"constructor"` 当成命中并返回原型对象，卡片于是渲染出 `[object Object]`（`textContent`，无 XSS 面，但是垃圾值）。2026-09-30 由评审提出并补守卫，用例锁在 `scripts/weather-city-catalog.test.mjs`（对抗性 `region` 必须落回 `areaName`）。可推广的一般规矩：**客户端里凡用网络字段做对象键，先 `hasOwn`**；数字键（如 `weatherIcons[Number(code)]`、`/domain/` 的 `messages[error.code]`）撞不到原型键，不需要这层守卫。
- 城市目录 `public/weather/city-catalog.js`（**生成文件、随仓库跟踪、不参与 `pnpm build`**）：367 个地级市与直辖市的 `[中文名, 纬度, 经度]`，坐标 1 位小数，8.2KB / gzip 3.8KB。数据源是阿里 DataV 行政区划图集 `geo.datav.aliyun.com/areas_v3/bound/<adcode>_full.json`，取 `properties.level === "city"` 的 `name` + `center`。再生成：`pnpm build:weather-cities`（显式运行，需网络）。名字归一在 `scripts/build-weather-cities.mjs` 的 `shortName()`：先砍 `自治州|自治县|地区|盟|林区|市` 后缀，再从第一个民族标记处截断（`伊犁哈萨克自治州`→`伊犁`、`德宏傣族景颇族自治州`→`德宏`、`西双版纳傣族自治州`→`西双版纳`），归一后撞名就退回全名（`海南藏族自治州` 与 `海南省`）。**不要用 GeoNames 替代**：它按聚落收录，市辖区各自成条（浦东/宝安/樊城 离坐标更近）、历史名混在别名里（迪化）、繁简不分（衡陽），调人口门槛治不好，实测命中率只有 74–89%。

- **卡片内部版式（2026-09-29 retro-tuning 定稿）**：主视觉行是「图标 + （温度上、天气状态下）」成一组、地名单独贴右缘（`align-self: start` 再加 `padding-top: 9px`，让地名与大数字读作同一水平线，而不是浮在右上角）；其下是**通栏参数行** `体感 32° │ 风速 11 km/h │ 湿度 75%`，每格是「图标 + `__detail-label`(11px 弱) + `__detail-value`(12px/500 强)」，第 2、3 格靠 `border-left 1px #e6e6e6` 分隔；截断落在 `__detail-value` 上（`min-width:0` + `overflow:hidden` + `ellipsis` + `nowrap`），标签是站内固定文案不参与截断；页脚是**组件状态栏** `数据：wttr.in 15:15`（时间不再带「获取于」，它与来源之间的可见间距是 `.weather-widget__time` 的 `margin-left: 5px`，**不是文本空格** —— 判据若按文本写必须容忍 innerText 在行内元素间补的空格）。层级只靠字号/字重/对齐/间距，不靠颜色。实测：卡片 253×113.2px，六档视口高度恒定、零横向溢出、参数行从不截断。
- **参数行的列宽必须是「内容定宽 + 两端铺满」，不是等宽**：`grid-auto-columns: minmax(0,auto)` + `justify-content: space-between`。等宽三格在加图标后不成立——实测每格 77.7px、去掉内距只有 63.7px 可用，而「图标+风速+`11 km/h`」需要 86px，`1fr` 会把单位截成 `11 k…`；三格按内容共需 249px > 行宽 233px，所以还得把格内内距 7→5、gap 3→2、图标 11→10 才装得下（现况：三格 `truncated:false`、`deadRight 0`）。「风」这个标签也已按站主意思改成「风速」，两字标签是容量被压扁的直接原因之一。
- **量「有没有铺满」绝不能用 `scrollWidth > clientWidth`**：不溢出的块级元素两者恒等，这个比值永远报「零空洞」，上一版就是用它把参数行右侧真实的 48.8px 死区（占行宽 21%）读成了 0。正确度量是**最后一格右缘到行右缘的距离**（`row.right - lastCell.right ≤ 1`），且截断要用**注入超长值**验证真的咬得住（断言值元素 `scrollWidth > clientWidth`、计算值为 `ellipsis`、且行的宽高一位都不许变）。
- **参数行的三个字段来自同一份 j1 响应**（`FeelsLikeC` / `windspeedKmph` / `humidity`），零额外请求、零新上游；缺失时 `weather-service.js` 归一为 `null`、`sidebar-widget.js` 让整行 `hidden`，不留空带。**风向 `winddir16Point` 有意不显示** —— 它是英文十六方位，加进来等于再养一层翻译。站主 2026-09-29 明确放开原先「不做湿度」的 Out of Scope（改判记录在 SPEC 的 Out of Scope 节），但今日高低温、空气质量与天气预警仍然不做。
- **天气壁纸层（2026-09-30 站主裁决引入）**：卡片主体区不再是纯色，`.weather-widget-body` 上叠**两层伪元素**——`::before` 是 7 张摄影壁纸之一（按 kind 换 `background-image`），`::after` 是**上轻下重的白纱渐变**，两层都 `position:absolute; inset:0; pointer-events:none` 且用负 `z-index`（-2 / -1）压在 in-flow 文字之下。四条承重事实：① `.weather-widget-body` 的 **`isolation: isolate` 不可删**——没有它，负 z-index 的壁纸会掉进祖先的白底之下，整层直接不可见（不是变淡，是看不见）；② **纱必须独立成层**，不能把「上浓下淡」烘进图片 alpha：主体区实测 **253×113 CSS px**，`background-size: cover` 后各张只显竖向 **59–80%**，烘进图片的话挪 `background-position` 时纱会跟着照片一起跑，文字区就漏了；③ `overflow: hidden` 是为 hover 的 `scale(1.05)` 兜边（`#sidebar` 那道 overflow 在 255px 外，兜不住单卡），实测焦点框未被裁：`[data-weather-retry]` 最紧处 bottom 5px / left 6px，`[data-weather-source]` bottom 5.9px，全为正；④ 浓度数值**单源于** `.weather-widget-body` 的五个自定义属性 `--bg-photo-opacity` / `--bg-photo-opacity-hover` / `--bg-veil-top` / `--bg-veil-bottom` / `--bg-photo-saturate`，侧栏烟测的对比度像素门**读前四个**而不是重抄，所以改浓度不用改测试（第五个不进对比度计算，理由见下）。
    - **浓度是站主 2026-09-30 的明确取舍：牺牲小字 AA 换彩色感**。卡内除 36px 温度是 `var(--text)` = `#000` 外，**其余文字全是 11–13px 的 `#666`**（`#sidebar, #sidebar a{color:var(--colorful-text-secondary)}` 约 5200 行继承而来），AA 小字要 4.5:1；有效浓度 = 照片 α ×（1 − 该处纱 α），守住 AA 的上限只有静止 **0.18** / hover **0.26**（实测 4.97 / 4.64）。站主看过六档实测曲线后仍选择越线，现值是 **静止 0.30 / hover 0.40、纱 0.45→0.82、饱和 ×1.35**，代价 **静止 4.12:1 / hover 3.66:1**（跌破小字线 4.5，仍高于大字线 3.0）。**这不是待修项，别拿 AA 当理由回退**；要再浓只有两条路——改卡内文字颜色，或加高卡片单独留无字图带（后者与同日「每页 10 条让分页回到底部」直接对冲），两条都需重新裁决。
    - **`saturate()` 是保亮度变换（L' = L），提饱和几乎不花对比度**：实测同浓度下 ×1 与 ×1.35 的最坏比值只差 0.01（0–255 取整噪声），彩色度却从 4.3 涨到 5.8。这是该曲线上唯一近乎免费的一步，也是对比度门**不读** `--bg-photo-saturate` 的原因。
    - 对比度门因此从「≥4.5」改成「**静止 ≥4.0 / hover ≥3.5**」：它现在守的是这次裁决承诺的下限，不是 AA；再往浓走会被这条当场拦下而不是静默通过。变异验证做过（注入 α=0.95 时七类 2.39–4.10 全部翻红）。
    - 显示时机：**只在有天气数据时**（`success` 与 stale 都算，靠 `sidebar-widget.js` 镜像到卡片根的 `data-weather-kind`；图标那份是既有的、判据读它，勿合并）；定位中/定位失败/无 JS 时属性不存在、两层伪元素整个不成立。stale 态壁纸**与成功态完全一样**，不去饱和不降档（站主裁决）。`/domain/` 终端行**不做**壁纸。
    - **hover 时图标与壁纸两处各自动是站主裁决，不是遗漏**（2026-09-30 明确否决了「削掉图标的 `rotate(-3deg)` 让位给壁纸」的建议）：触发面同用 `.widget:has(.weather-widget-body):hover`，所以是同一个手势一起响应。`prefers-reduced-motion` 下撤壁纸的 `scale` 与入场淡入、**保留**不透明度变化。入场只淡照片层，白纱不参与动画，淡入全程文字被完整护住。

## 加入文章的流程

当用户提到从某个特定的文件导入现有文章时，请遵循以下流程（期间参考已有文章的实现）

1. **定位源文件**：在用户指定位置（如桌面）找到外部 `.md`；含中文内容时按 chinese-encoding 规范以 UTF-8 读取。
2. **创建文章**：建 `src/content/posts/<yyyymmddhhmmss>/index.md`（目录名即 slug，硬规则见上节；`published` 必须与目录名对应）。
3. **代拟 frontmatter**：`title` 取原文 H1；`description` 按文中事实撰写；`category`/`tags` 对齐既有文章用法；`draft/private/views/comments/hotness` 给默认值。不设 `image` 时封面走 `getCover()` 的 hash 随机图兜底。
4. **迁移图片资源**：源文引用的本地图片（如 Typora 的 `typora-user-images`）复制到 `public/images/posts/<yyyymmddhhmmss>/`，正文图片路径重定向为 `/images/posts/<yyyymmddhhmmss>/<文件名>`。
5. **正文逐字保留**：不修错别字、不改标点/引号样式、保留原文主体示例；仅允许结构调整——原文 H1 移入 `title` 后正文不再保留（`[...slug].astro` 用 title 渲染 `<h1>`，重复会显示两次标题），以及第 4 条的图片路径重定向。
6. **逐字节校验**：用脚本 diff"原文（做过路径替换、去掉首行 H1）"与"新文件正文（剥掉 frontmatter）"，逐行严格比较确认零差异；发现差异必须改回与原文一致。
7. **头图（可选）**：你需要询问清楚用户关于文章的头图信息，例如，你可以从文中截图生成 `<主题>-cover.jpg` 放同图片目录——缩放至 1320×880、JPEG q85（详情页封面桌面最大显示 660 CSS px，`sizes` 见 `[...slug].astro`，×2 DPR = 1320；源宽 1320 > 1080×1.2，下次 build 命中 1080 档 WebP 变体 + LQIP；dev 环境直接显示原图属正常），frontmatter `image:` 指向它。
8. **GitHub 卡片（可选，文末裸仓库链接适用）**：`https://github.com/<owner>/<repo>` 改为 `::github{repo="owner/repo"}`（与既有文章同语法），随后运行 `pnpm fetch-repos` 增量拉取元数据缓存。**顺序坑**：先改文章、后拉缓存时，dev 的 content layer 会把"缓存缺失→回退链接"的渲染结果缓存住（即下方 ⚠️ 大坑警告在新增 `::github` 引用场景的表现）；对内容文件再做一次真实改动（如追加并收敛尾部换行）触发重渲染即可，remark 插件每次转换惰性读 JSON，无需重启 dev。文件尾部保持单个换行过 Prettier check。
9. **验证与提交**：提交前对 `src/` 下改动文件跑 `pnpm exec prettier --write`——lint.yml 只查 `./src`（根目录 AGENTS.md 不在内），手写 `index.md` 的 `*emphasis*`/`***bold-italic***` 会被 Prettier 归一化为 `_…_`/`_**…**_`（remark 管线语义等价转换，渲染输出不变，文字零变动，可直接放行）。提交后确认 Lint / Build and Check / Deploy 三条工作流全绿；dev 服务器请求 `/posts/<slug>/` 返回 200、HTML 含标题与图片引用、各图片 URL 返回 200；含 `::github` 引用时确认卡片为完整态（有 `github-card-name`、无 `github-card-error`——注意 dev 下样式表文本也含该类名，须查卡片标记而非全局字符串）；用户要求自行验证时不要代做浏览器检查以外的多余操作。

## ⚠️ 大坑警告：Astro content layer 缓存会"吃掉"插件改动（本地与 CI 都会踩）

**症状**：修改了 remark/rehype 插件（或任何影响 Markdown 渲染的逻辑）后构建，产物仍是旧 HTML，全程无任何报错。本地和线上都可能发生，2026-08-31 两侧均已实际踩坑。

**根因**：Astro 5 content layer 会把渲染结果缓存到 data store；内容文件未变时构建直接复用缓存、**不重跑插件**；touch 内容文件 mtime 也无法使其失效。当前命令可能在 `node_modules/.astro/data-store.json` 或 `.astro/data-store.json` 生成 data store，不能只依赖其中一处。

**本地规则**：改插件逻辑后先删除 `node_modules/.astro/`，并在存在时删除 `.astro/data-store.json`，再构建。

**CI 规则**：`withastro/action` 默认 `cache: true` 会跨 run 缓存 `node_modules/.astro`，同样复用旧渲染——**`deploy.yml` 已传 `cache: false` 关闭，任何 workflow 改动都不得恢复该缓存**。`build.yml` 用 `setup-node`（仅缓存 pnpm store）不受影响。

**CI 执行拓扑**：Pull Request 由 `build.yml` 执行 `Astro Check` 和完整 `Astro Build`，`lint.yml` 执行 Prettier 检查；`main` push 时 `build.yml` 的 `Astro Build` job 通过 `if: ${{ github.event_name == 'pull_request' }}` 跳过，完整构建只由 `deploy.yml` 执行一次后部署。`deploy.yml` 也支持 `workflow_dispatch`，并通过 `concurrency` 取消同一 workflow/ref 的旧部署。

**线上验证部署是否生效**：Fastly 边缘缓存 HTML `max-age=600`，且缓存键不含查询串（加 `?cb=` 无效）；看响应头 `Last-Modified` 是否晚于部署完成时间，或下载 Actions run 的 `github-pages` artifact 直接查 HTML（确定性验证）。
